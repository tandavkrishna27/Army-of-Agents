## Track: runtime

### R1-zombie-cli-survives-cancel — effort: medium
**Root cause:** Four stacked defects. (1) Windows kill is single-process, never tree: packages/adapter-utils/src/server-utils.ts:71-86 signalRunningProcess on win32 calls child.kill(), and children are spawned with shell:true on Windows (server-utils.ts:343) — so the direct child is the cmd.exe wrapper and the real claude CLI is a grandchild that survives as an orphan. The code comment at server-utils.ts:59-65 explicitly admits this ('would need taskkill /PID <pid> /T /F. Tracked as a follow-up'). (2) cancelRun's SIGKILL escalation is dead code: server/src/services/heartbeat.ts:5487-5551 sends SIGTERM (5504), schedules SIGKILL after graceSec guarded by runningProcesses.has(run.id) (5510), but line 5547 deletes the entry immediately — the grace timer always early-returns. (3) The dead cmd.exe doesn't end the adapter await: runChildProcess resolves on the child 'close' event (server-utils.ts:483), which waits for stdio to close; the orphaned grandchild holds the inherited pipes, so adapter.execute stays pending ~15 min → the finally at heartbeat.ts:4166-4169 never runs → the W5b hook token stays registered (24h TTL, heartbeat.ts:4123) → zombie PreToolUse POSTs still resolve a live broker (routes/runtime-hooks.ts:67). (4) No terminal-status latch: setRunStatus (heartbeat.ts:1657-1667) is an unconditional UPDATE, and the broker's markRunWaiting/clearRunWaiting (heartbeat.ts:4080-4093) write status 'running' unconditionally — every zombie hook POST → broker createPrompt (heartbeat.ts:274-312, markRunWaiting at 310) flips cancelled→running. agent-runtime-decisions.ts createPrompt (663-709) never checks run status, so zombie decisions mint freely; each expires via the 30s sweep (index.ts:1058-1081) emitting an agent_error (agent-runtime-decisions.ts:984-1000). The 'first cancel didn't stick' is the same lost-update: cancel writes cancelled, an in-flight/next markRunWaiting writes running milliseconds later; the reap sweeper never catches it because markRunWaiting keeps bumping updatedAt (heartbeat.ts:2205-2207); and while the row reads 'cancelled' during a flap, cancelRun's early return at 5490 (status not running/queued → return) means a re-cancel doesn't even signal the process. The second manual cancel landed during a 'running' phase, re-ran cancelActiveForRun, the pending decision got cancelled, waitForAnswer threw RuntimeDecisionCancelledError, the hook denied, and the CLI wound down.

**Built:** Cancel plumbing exists end to end: POST /heartbeat-runs/:id/cancel → cancelRun (heartbeat.ts:5487) with SIGTERM + intended SIGKILL escalation, wakeup cancellation, runtime-decision cleanup (cancelRuntimeDecisionPromptsForRun → cancelActiveForRun, agent-runtime-decisions.ts:1023-1052), issue release, next-queued-run start. POSIX side is actually correct: detached:true spawns (server-utils.ts:347) + process-group kill (process.kill(-pgid), server-utils.ts:75-78) reap the whole tree. spawnTrackedChild even has a correct terminate() with working escalation (server-utils.ts:364-373) that cancelRun doesn't use.

**Missing:** (a) Any process-tree kill on Windows; (b) a working SIGTERM→SIGKILL escalation in cancelRun (dead due to the eager map delete); (c) a terminal-status latch so markRunWaiting/clearRunWaiting/late adapter completion (heartbeat.ts:4307, 4513) cannot resurrect a cancelled run; (d) a run-liveness guard in createPrompt so a terminal run cannot raise new runtime decisions; (e) hook-token deregistration on cancel (the finally-only cleanup assumes adapter.execute returns promptly).

**Fix design:** Four coordinated changes. (1) win32 tree-kill in signalRunningProcess (packages/adapter-utils/src/server-utils.ts): when process.platform==='win32' and child.pid is set, spawn('taskkill', ['/PID', String(child.pid), '/T', '/F']) fire-and-forget (no shell), for both TERM and KILL requests — Windows has no graceful signal, document that supervised CLIs get hard-killed; swallow the 128 'not found' exit. Keep the POSIX group-kill unchanged. (2) Fix teardown ordering in heartbeat.ts: delete the eager runningProcesses.delete(run.id) at 5547 (and the equivalents at 5585/5630/5667) — deregistration is already owned by spawnTrackedChild's close/error listeners (server-utils.ts:357-362) — so the grace-escalation timer's has() check works; with (1), taskkill /T /F makes escalation mostly moot on Windows but the fix keeps POSIX honest. (3) Terminal-status latch in setRunStatus (heartbeat.ts:1657): make the UPDATE conditional — WHERE status NOT IN ('succeeded','failed','cancelled','timed_out') when the requested status differs; on guard miss, apply a metadata-only patch (usageJson, log excerpts, excerpts) without touching status and skip the live event + terminal hub emit (prevents duplicate run_failed items and makes markRunWaiting/clearRunWaiting/late-completion no-ops on cancelled runs). markRunWaiting still works on live runs since running→running passes. (4) Zombie-decision guard: in agentRuntimeDecisionService.createPrompt (agent-runtime-decisions.ts:663) load heartbeatRuns.status for input.runId and throw conflict('run is terminal') when terminal — the hook route's catch (routes/runtime-hooks.ts:93-100) maps it to deny, so the zombie's tools are refused instead of minting decisions that later expire into agent_error noise. Belt-and-suspenders: add deregisterRuntimeHooksForRun(runId) to runtime-hook-registry.ts (iterate the Map) and call it from cancelRun. Tests: unit — setRunStatus latch (cancelled + 'running' patch → status unchanged, metadata applied); broker test — createPrompt against a cancelled run throws and hook route returns deny; win32 signal test mocking spawn for taskkill; existing cancel tests keep passing.

**Product questions:** none — one technical tradeoff to be aware of: taskkill /F is forceful, so on Windows a cancelled agent CLI gets no graceful-shutdown window (it doesn't meaningfully get one today either; child.kill is already TerminateProcess).

### R2-work-question-stall-and-no-caller — effort: small
**Root cause:** Two distinct gaps. STALL: relay only happens inside the in-run broker — waitAndRelay (server/src/services/heartbeat.ts:314-371) is the sole path to markRelayed/markRelayFailed (grep confirms heartbeat.ts:354 is markRelayFailed's only production caller). answerPrompt (server/src/services/agent-runtime-decisions.ts:799-872, route routes/agent-runtime-decisions.ts:112-130) performs zero run-liveness checks; it flips the row to 'answered' (non-terminal, in ACTIVE_STATUSES:20-25) and re-emits the still-open hub item (line 870). The expiry sweep only sees statuses created/shown (listDueForExpiry, agent-runtime-decisions.ts:494-497), so an 'answered' decision whose run is dead is invisible to every janitor: no relay, no expiry, no reconcile-close (runtimeDecisionSourceSnapshot:510-532 says non-terminal → keep open). Note the QA report's 'expires_at NULL' was an artifact of the SQL seed — real createPrompt defaults work_question TTL to 24h (agent-runtime-decisions.ts:33, 669-670) — but that TTL is irrelevant once status='answered'. NO CALLER: broker.askWorkQuestion exists (heartbeat.ts:460-469) with zero production call sites (only tests; the codex W5c bridge test even asserts it must NOT be called, packages/adapters/codex-local/src/server/__tests__/appserver-approval-bridge.test.ts:41). W5b deliberately scoped it out: 'AskUserQuestion is SDK-only — no clean CLI interception' and 'the work_question kind is DEFERRED' (docs/aoa/plans/2026-07-03-w5b-first-adapter-runtime-bridge-plan.md:19,32). So the entire agent-asks-founder feature — service, broker, answer route, RuntimeDecisionPanel answer textarea — is reachable only by SQL seeds.

**Built:** Full downstream machinery: work_question kind in the decision service (create/answer/waitForAnswer/relay states, 24h default TTL, park_run default timeout policy at agent-runtime-decisions.ts:39-41), answer validation schema (packages/shared/src/validators/hub.ts), founder answer route with optimistic concurrency, RuntimeDecisionPanel answer UI in the hub viewer, broker.askWorkQuestion wired into every heartbeat run's runtimeDecisionBroker (heartbeat.ts:4072-4094), and the 30s expiry sweep (server/src/index.ts:1058-1081).

**Missing:** (a) Answer-time run-liveness check; (b) sweeper coverage for 'answered' (and stranded 'relay_failed') rows with dead runs; (c) any adapter or harness that ever calls askWorkQuestion — this last item is a FEATURE, not a bug fix.

**Fix design:** SAFETY FIXES (small, ship now): (1) answerPrompt liveness gate — after loading the row (agent-runtime-decisions.ts:800), fetch heartbeatRuns.status for row.runId; if terminal/missing, do NOT record the answer: flip the decision to cancelled (relayError 'run ended before the answer could be delivered'), closeProjectedHubItem, and throw 409 with that message so the founder sees an honest error instead of a forever-'answered' ghost. (2) Stranded-answer sweep — extend the 30s sweep with svc.sweepStrandedAnswers({limit}): select decisions status IN ('answered','relay_failed') joined to heartbeatRuns where run status is terminal OR answeredAt < now()-10min; flip to cancelled with relayError 'answer was never picked up by the run', emit an agent_error notifications-lane follow-up (reuse the parked-emit block pattern at agent-runtime-decisions.ts:984-1000 with title 'Answer could not be delivered: <title>'), then closeProjectedHubItem. This catches answered-then-run-died and any relay crash. (3) No TTL change needed — document that the seed row's NULL expires_at can't occur via createPrompt. FEATURE (separate, medium-large — scope honestly as the W5b-deferred work_question bridge): recommend ask-then-park over sync-block. Claude Code headless has no AskUserQuestion hook to intercept, and org-agent heartbeat runs attach no MCP servers (the W5b settings file contains only a hooks key — runtime-hook-settings tests assert no mcpServers). Design: add POST /internal/runtime-hooks/work-question (mirror of routes/runtime-hooks.ts, authed by the same per-run hook token) or an MCP ask_founder tool; it calls createPrompt(kind=work_question) and returns IMMEDIATELY with 'question recorded — finish what you can and end your turn; you will be re-woken with the answer'. The run ends normally (parked at the task level). answerPrompt then relays by re-dispatch instead of broker: enqueue a heartbeat wakeup for the agent with contextSnapshot {decisionId, answerPayload, issueId} resuming the task session (agent_task_sessions resume mapping already exists), and markRelayed on successful enqueue. This eliminates the dead-run relay class for work_question entirely and needs no CLI interception — the prompt template instructs the agent to call the endpoint via curl using AOA_API_URL (buildAoaEnv, packages/adapter-utils/src/server-utils.ts:162-180) + the hook token env. Pieces: endpoint + prompt-template instruction + relay-by-wakeup in answerPrompt + resume-context injection + docs; roughly W5b-sized.

**Product questions:** For the safety fix: when a founder answers a dead-run question, reject-with-409-and-cancel (recommended — honest, no ghost state) vs record-the-answer-then-mark-relay_failed (preserves the founder's composed answer but keeps an urgent item alive that can never relay)? For the feature: (1) sync-block (agent waits in-run, 5-min SLA like permissions) vs ask-then-park-and-rewake (recommended — fits the heartbeat push model, survives founder-away-for-hours, but each answer costs a new run/wakeup); (2) should the answer auto-re-wake the agent (spends budget without an explicit dispatch) or park the task for manual re-dispatch? Recommend auto-re-wake gated by the same preflight budget check used for crew dispatch.

### R3-runtime-decision-hub-actions-not-server-blocked — effort: small
**Root cause:** recordLifecycleAction (server/src/services/hub-items.ts:881-1058) gates resolve/archive only on founder-vs-not authority (928-934, via authorityForSemanticType, packages/shared/src/hub.ts:120-132) — there is no per-type action-legality check — and the action route (server/src/routes/hub-items.ts:169-215) forwards any of resolve/archive/claim/release. **Built:** Server-side authority gating (founder-gated types 403 for non-founders), version-guarded transitions with audit rows + idempotency, claim/release gates, personal state (dismiss/snooze/read) via applyPersonalState (hub-items.ts:771), system reconcile closes via applyGuardedTransition directly (hub-items.ts:1595-1618, actorType system) — importantly NOT via recordLifecycleAction, so a new per-type guard cannot break push-close/reconcile. **Missing:** A per-type manual-lifecycle legality gate in the service layer; removal of the unreachable recordAndAct tail (and arguably the whole function). Adjacent but distinct: resolve/archive on approval_request/join_request items also has zero source effect and permanently hides a still-pending approval from the whole board (audit §3 gap 2).

**Fix design:** (1) Add to packages/shared/src/hub.ts a manual-lifecycle legality map, e.g. HUB_MANUAL_LIFECYCLE_BLOCKED_TYPES: agent_runtime_decision blocks all four shared actions (resolve/archive/claim/release — claim/release are moot since the producer never sets ownerPool=board, but block for completeness). (2) Enforce in recordLifecycleAction immediately after the open-status check (hub-items.ts:922-926): throw conflict/403 'Runtime decisions are decided in the decision panel — answer them or let the timeout policy handle it'. Because the route, bulkAction, and autopilot applyEvaluation all funnel through recordLifecycleAction, one guard covers every surface; system reconcile + push-close are untouched (they call applyGuardedTransition directly). Make the block STATIC per-type, not conditional on source state: after BUG-2 push-close there is no legit reason to manually close a runtime_decision item — terminal decisions archive automatically (push-close + GET sweep heals any miss), and a conditional 'allow archive when source is terminal' would just re-implement the reconciler with a race window. Keep dismiss/snooze/read allowed (personal, per-user visibility only; the shared item and the pending decision stay live and sweepable — matches the UI, which still offers them). (3) Dead code: delete hub-items.ts:1284-1346, then delete recordAndAct entirely plus its export at 1758 and port its two test files to call recordLifecycleAction directly (same semantics, richer return: {item, auditId, undoDeadline}); if churn-averse, a 10-line delegating wrapper is acceptable but deletion is the honest end-state. (4) Tests: POST action resolve+archive on an open agent_runtime_decision → 409 with the guidance message; bulk-archive batch containing one runtime-decision item → that item reported failed, others succeed; reconcile_close and push-close still archive; UI needs no change (buttons already hidden). Edge case: history-tab items are non-open so the existing status check (922) already 409s them — no interaction with the new guard.

**Product questions:** (1) Should dismiss/snooze also be blocked on pending runtime decisions? Recommend NO — they are per-user visibility with a safety net (timeout policy + agent_error follow-up), and removing them leaves a founder no way to triage a prompt they cannot answer yet; but if the stance is 'a pending permission prompt must never be hideable', block dismiss too and keep snooze. (2) Extend the same manual-close block to approval_request/join_request (whose resolve/archive likewise never decides the source and permanently hides a pending approval from every user)? Options: (a) extend the block — consistent 'decide at the source' model, cheapest, recommended as a fast-follow; (b) wire side-effects so hub resolve = approve — rejected-worthy: overloading a generic lifecycle verb with an irreversible governance decision invites misclicks and complicates undo.
