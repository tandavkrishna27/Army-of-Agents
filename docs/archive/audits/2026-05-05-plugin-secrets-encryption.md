# Plugin Secrets Encryption Audit (2026-05-05)

## Scope

Audit of `server/src/services/plugin-secrets-handler.ts` and supporting
infrastructure for encryption-at-rest of secrets stored in the
`company_secrets` table — with focus on `github_pat` (used by the Phase I
worktree feature's "Create PR" button via `server/src/routes/github.ts` and
`server/src/services/github-pr.ts`).

Reviewer of PR #118 recommended a targeted security audit. This document
captures the findings.

Audited at commit `8003b3b` on branch `Porting1.1`.

## Architecture summary

Secrets are stored in two normalized tables —
`company_secrets` (one row per logical secret, with `provider` + name)
and `company_secret_versions` (immutable rotation history with the encrypted
`material` JSONB blob). Encryption is delegated to a `SecretProviderModule`
abstraction (`server/src/secrets/types.ts:7`) registered in
`server/src/secrets/provider-registry.ts:11-16`. Four providers are wired in,
but only `local_encrypted` is functional today —
`aws_secrets_manager`, `gcp_secret_manager`, and `vault` are stub
implementations whose `createVersion` and `resolveVersion` both throw
`unprocessable("<id> provider is not configured in this deployment")`
(`server/src/secrets/external-stub-providers.ts:15-21`). All real
encryption/decryption happens in `server/src/secrets/local-encrypted-provider.ts`.

`plugin-secrets-handler.ts` is the host-side adapter for plugin workers calling
`ctx.secrets.resolve(secretRef)` — it validates the ref, scopes resolution to
secrets actually referenced by that plugin's config, rate-limits, then
delegates to the appropriate `SecretProviderModule`. It is **not** the
write path for `github_pat`; that path lives in `server/src/routes/github.ts`
calling `secretService.create()` (`server/src/services/secrets.ts:171-218`).

## Provider implementations audited

### local_encrypted (active, default)

File: `server/src/secrets/local-encrypted-provider.ts`

- **Algorithm:** AES-256-GCM (authenticated encryption with associated data)
  via Node `node:crypto` (`createCipheriv("aes-256-gcm", masterKey, iv)`,
  line 81).
  - 12-byte IV generated by `randomBytes(12)` per encryption (line 80) — fresh
    nonce per call, no reuse risk.
  - Auth tag (`cipher.getAuthTag()`) stored alongside ciphertext (line 83);
    `decipher.setAuthTag(tag)` on decrypt (line 97) ensures integrity is
    verified before plaintext is returned.
  - Persisted material shape: `{ scheme: "local_encrypted_v1", iv, tag,
    ciphertext }`, all base64. The `scheme` discriminator allows future
    rotation to a new encryption algorithm without breaking existing
    ciphertext (verified at decrypt time via `asLocalEncryptedMaterial`,
    line 102-114).
- **Key source:** Two-tier resolution (`loadOrCreateMasterKey`, line 41-73):
  1. `AOA_SECRETS_MASTER_KEY` env var (preferred). Accepts 32-byte hex (64
     chars), base64 (32 raw bytes), or 32-char raw UTF-8 string. Invalid
     formats throw `badRequest`.
  2. File at `AOA_SECRETS_MASTER_KEY_FILE` (default
     `<cwd>/data/secrets/master.key`). If missing, **a fresh random 32-byte
     key is generated via `crypto.randomBytes(32)`** and persisted to disk.
- **Key persistence:** `writeFileSync(keyPath, …, { mode: 0o600 })` followed
  by `chmodSync(keyPath, 0o600)` (line 66-71). The directory is created
  with `mkdirSync(..., { recursive: true })` — no permission control on the
  parent directory.
- **Key rotation:**
  - Per-secret rotation: `secretService.rotate()` creates a new
    `company_secret_versions` row with a fresh ciphertext under the same
    master key (`server/src/services/secrets.ts:220-258`). The previous
    version is preserved; the secret row's `latestVersion` is bumped
    atomically.
  - Per-master-key rotation: not implemented. The `scheme:
    "local_encrypted_v1"` discriminator reserves the design space for a
    future migration but no migration code exists, no second-key support
    exists, and no audit log of which key encrypted which version exists.
- **Failure mode:** If the master key is lost or rotated unrecoverably,
  `decipher.final()` throws (GCM auth-tag mismatch). The error propagates
  through `resolveSecretValue` and surfaces to the caller. `github-pr.ts:81`
  catches the throw and re-raises as
  `GitHubPrError("GitHub PAT could not be decrypted", 500)` — clean failure,
  no leakage of the underlying crypto error or PAT material.

## Writing path (UI → DB)

For `github_pat` specifically (Phase I worktree "Create PR" feature):

1. **UI:** `ui/src/components/GitHubIntegrationCard.tsx:152-176` renders an
   `<input type="password">` for the PAT. Submitted via mutation as
   `{ pat }`.
2. **Route:** `server/src/routes/github.ts:33-79`
   `POST /companies/:companyId/github/pat`:
   - Asserts `board` actor + company access (line 34-35).
   - Zod validates `{ pat: z.string().min(1) }` (line 38).
   - **Verifies the PAT against GitHub** by calling
     `octokit.users.getAuthenticated()` before storing (line 46-47). If
     GitHub rejects, returns 400 — invalid PATs never hit the DB.
   - Idempotent: deletes any existing `github_pat` row first (line 55).
   - Stores via `secretService.create()` (line 56-66):
     `{ name: "github_pat", provider: "local_encrypted", value: pat,
       externalRef: githubUser }`. The `value` (plaintext PAT) is passed
     into `provider.createVersion()` (`server/src/services/secrets.ts:185-189`),
     which calls `localEncryptedProvider.createVersion()` →
     `encryptValue(masterKey, input.value)`. Only the encrypted material
     and `sha256` of the value are persisted; the plaintext is NOT
     persisted to `company_secrets` or `company_secret_versions`.
   - Activity log entry uses the secret-row UUID as `entityId` and includes
     only `{ githubUser }` in details (line 68-76) — never the PAT.
   - Response payload is `{ configured: true, githubUser }` (line 78) — PAT
     never echoed back.
3. **DB:** `companySecretVersions.material` column is `jsonb` (`packages/db/
   src/schema/company_secret_versions.ts:11`). Stored shape is the
   `LocalEncryptedMaterial` object, all components base64-encoded
   ciphertext + IV + tag — no plaintext.
   - `valueSha256` (`text`) is also persisted (`schema/...:12`). This is a
     deterministic hash of the plaintext used for dedup/lookup. SHA-256 of
     a high-entropy GitHub PAT (40+ chars of random alphanumerics) is
     pre-image-resistant in practice, so this does not constitute
     plaintext leakage.

## Reading path (DB → use site)

For `github_pat` specifically:

1. **Route:** `server/src/routes/github.ts:130-222`
   `POST /issues/:issueId/github-pr` validates body, looks up the issue +
   workspace, and calls `createPullRequest(db, …)` (line 167).
2. **Service:** `server/src/services/github-pr.ts:55-134`
   `createPullRequest`:
   - `secretService.getByName(companyId, "github_pat")` to find the row
     (line 68).
   - `secretService.resolveSecretValue(companyId, secretRow.id, "latest")`
     (line 79) — performs `assertSecretInCompany` (cross-company guard at
     `secrets.ts:71-76`), fetches the latest `company_secret_versions` row,
     and calls `localEncryptedProvider.resolveVersion()` →
     `decryptValue(masterKey, …)` to obtain plaintext.
   - **Plaintext PAT lifetime:** held in a single local `pat` variable
     (line 77) and passed straight into `new Octokit({ auth: pat })` on
     line 88. No logging, no reassignment to broader scope, no caching.
   - **Decryption errors are swallowed:** the `try`/`catch` on line 78-82
     re-throws as a generic `GitHubPrError("GitHub PAT could not be
     decrypted", 500)` — the original crypto error (which could leak some
     low-level GCM context) is dropped.
   - The function uses `try`/`catch` around the Octokit `pulls.create`
     call (line 90-133) and surfaces only HTTP status + scope hints — the
     PAT is not in the error path. (Octokit also strips the bearer token
     from its internal error objects by default.)
3. **Garbage collection:** `pat` is a function-scoped `let`. After
   `createPullRequest` returns, the variable falls out of scope and is
   eligible for GC. No persistence of the resolved value beyond the
   request.

## Logging behavior

- `server/src/secrets/local-encrypted-provider.ts` — **no logging**. Verified
  via grep `console.|logger.` (zero matches).
- `server/src/services/secrets.ts` — **no logging**. Same grep, zero matches.
- `server/src/services/plugin-secrets-handler.ts` — **no logging**. Same
  grep, zero matches. The module-level docstring explicitly notes
  "Resolved values are **never** logged, persisted, or included in error
  messages (per PLUGIN_SPEC.md §22)."
- `server/src/services/github-pr.ts` — **no logging**.
- `server/src/routes/github.ts` — **no logging**. Activity log entries
  (`logActivity` calls at line 68, 94, 199) include only metadata
  (`githubUser`, PR URL/number, workspace ID) — never the PAT.
- Errors surfaced to the client: all sanitised. The route returns
  `{ error: "Invalid GitHub PAT" }` (line 50) on PAT verification failure
  but the request body is not echoed back. `GitHubPrError` carries only
  human messages and scope hints — never PAT material.

## Findings

### High severity (action required immediately)

**None.** The encrypt-store-read-decrypt-use chain is sound:

- AES-256-GCM with per-call random 12-byte IV — modern, authenticated,
  no nonce reuse.
- Master key sourced from env var (preferred) or from a 0600-mode file —
  not hardcoded, not committed.
- Plaintext PAT is never logged, never persisted in plaintext, never
  echoed in API responses, and held only in request-scoped local
  variables.
- Errors are sanitised at every layer — neither the secret value nor
  underlying crypto details leak to the client or activity log.
- Cross-company access is blocked by `assertSecretInCompany` (`secrets.ts:71`).
- Plugin workers can only resolve secrets actually referenced in their
  declared config (`plugin-secrets-handler.ts:286-309`), with rate-limiting
  (30 attempts/min/plugin, line 254) to prevent UUID enumeration.
- A 5-second hash-vs-existing check is unnecessary because the
  `(companyId, name)` unique index forces idempotent overwrite.

### Medium severity (action recommended)

1. **Master key file permissions are not enforceable on Windows.**
   `local-encrypted-provider.ts:66-71` uses `writeFileSync(..., { mode:
   0o600 })` and `chmodSync(keyPath, 0o600)`. POSIX `0o600` is honored
   by Linux/macOS, but Windows NTFS does **not** apply POSIX mode bits in
   the way operators expect — the file inherits ACLs from its parent
   directory by default. Anyone with read access to the user profile
   (or another local admin / SYSTEM-context process) can read the master
   key on Windows installs. AoA documents Windows as a supported runtime,
   so this is a real exposure for Windows board operators. **Recommend:**
   surface a startup warning when the platform is `win32` and no env-var
   override is set, advising operators to either set
   `AOA_SECRETS_MASTER_KEY` (env var, e.g. via Docker secrets or a
   service-manager-controlled `.env`) or harden the directory ACL
   manually. The deploy doc at `docs/deploy/distribution.md` should
   call this out.

2. **Master-key rotation has no migration path.** The `scheme:
   "local_encrypted_v1"` discriminator reserves the namespace, but
   there is no second-key support, no migration tooling, and no audit
   trail of which key encrypted which version. If an operator suspects
   key compromise, the only recourse today is: (a) rotate every secret's
   value (tedious — requires re-entering every PAT, every webhook
   secret, every LLM API key), or (b) replace the master key, accept
   that all existing ciphertexts become unreadable, and force re-entry.
   **Recommend:** track this as a future enhancement — encrypt new
   versions under a new key, allow decrypt fallback to the previous key
   tagged by `keyId` in the material blob.

3. **`local-encrypted-provider.ts` has no direct unit tests.** The
   encryption primitives (round-trip, GCM tag validation, master-key
   resolution from each of three sources) are critical security code
   but exercised only transitively. **Recommend:** add a focused test
   suite that:
   - encrypts and decrypts known plaintexts and verifies round-trip
     equality;
   - verifies that tampering with `tag` or `ciphertext` causes
     `decipher.final()` to throw;
   - verifies env-var resolution accepts hex/base64/raw and rejects
     malformed input;
   - verifies the file-based fallback creates the file with the
     intended mode on POSIX platforms.

### Low severity / Recommendations

4. **`github-pr.ts:81` decryption-error path is uncovered.** Add a unit
   test that mocks `resolveSecretValue` to reject and asserts the route
   returns `{ error: "GitHub PAT could not be decrypted" }` with status
   500.

5. **`badRequest` is an odd error class for the encryption layer.**
   `local-encrypted-provider.ts:46`, `:58`, `:113` throw
   `badRequest(...)` from `../errors.js`. Semantically these are
   server-side configuration / data-integrity failures, not bad client
   input. They should probably surface as 500-class errors so that
   express's default error handler doesn't accidentally render them as
   400 responses with the underlying message visible to the caller.
   (Today, the route handlers wrap these — `github-pr.ts:80-84` swallows
   them — so the issue is latent. But future call sites could regress.)

6. **`valueSha256` is stored alongside ciphertext.** This is fine for
   high-entropy secrets like GitHub PATs (`ghp_…` is ~40+ chars of
   uniform random characters — pre-image attacks are infeasible). But if
   `secretService.create()` is ever used for low-entropy secrets (e.g.,
   a 6-digit PIN or a short shared key), the SHA-256 column becomes a
   trivial offline attack target. **Recommend:** document that
   `company_secrets` is only suitable for high-entropy values; or, if
   low-entropy is a real use case, consider salting the hash.

7. **`secretService.resolveByName` is a public method on the service.**
   `secrets.ts:163-167`. Any code with access to the `secretService`
   handle can resolve any secret by name, with no caller-side
   capability check beyond `companyId`. The plugin worker path
   (`plugin-secrets-handler.ts`) layers config-scope checks and rate
   limiting on top, but other callers — `transcription.ts:80`,
   `internal-agent/providers/index.ts:42`, `heartbeat.ts:703`,
   `routines.ts:571` — rely on their own context for scoping. This is
   working as designed today, but worth noting in case future code
   adds a less-trusted caller.

8. **Plugin handler's allowed-refs cache TTL is 30 seconds.**
   `plugin-secrets-handler.ts:258`. If a plugin's config is mutated to
   add a new secret reference, the worker cannot resolve it for up to
   30s. If a config is mutated to *remove* a secret reference, the
   worker can still resolve the now-unauthorized secret for up to 30s.
   The latter is the security-relevant direction. Probably acceptable
   given the threat model (operator-controlled plugins, not adversarial
   tenants), but worth documenting.
