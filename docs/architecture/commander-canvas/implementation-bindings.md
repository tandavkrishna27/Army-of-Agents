## Block and executable-tool checkpoint producer

E1.2 defines a separate proposed `universe_panel_checkpoints` table in `packages/db/src/schema/universe.ts`: UUID id, companyId/userId/conversationId, panelKey, sourceVersionId, schemaVersion, revision (zero on absence), bounded JSON data, timestamps; unique owner/company/conversation/panelKey/sourceVersionId. This is personal presentation state under the same owner checks as layout. It is not a task table, job queue or grant store. E5.1 supplies the reviewed `BlockCheckpoint` payload schema; E5.2 supplies a registered, inert tool checkpoint schema. Neither renderer registers arbitrary executable validators.

E1.2's `universeStateService` adds `getCheckpoint(scope,key,sourceVersionId)` and `saveCheckpoint(scope,key,input)`. Proposed GET/PATCH `/api/companies/:companyId/universe/conversations/:conversationId/panels/:panelKey/checkpoint`; GET query identifies sourceVersionId; PATCH body `{sourceVersionId,schemaVersion,expectedRevision,data}`. Authenticate conversation owner and exact accessible source version, decode panelKey once as a bounded opaque identifier, validate registered schema and serialized size ≤32 KiB. Under row lock compare expectedRevision and update or return 409; absent row expects zero. No unscoped raw checkpoint endpoint.

On close, retain checkpoint and unsent form inputs according to draft policy; remove only the live panel. New source version gets separate state. Minimize, navigation and reload cannot replay an action. E1.3 stores pending action/submission metadata separately from editable checkpoint content. Consumer sees `{revision,data}` and retains local dirty variant on conflict. Whole-layout patches do not carry checkpoint JSON; the 64 KiB layout patch bound remains independent.

Implementation tests: same-source two-tab conflict preserves both variants; different instances/versions independent; reload restores input without dispatch; same-company other-user denied; foreign source/version denied; 32 KiB boundary and unknown schema rejected; close/reopen retains state; reset Appearance does not delete it. Add `server/src/__tests__/universe-checkpoints.integration.test.ts` and E5 connected host test. The migrated DB fixture is E1.2's actual PostgreSQL setup. This producer is specified concretely in E1.2/1 and its slice outline after H1 reconciliation; it has not been implemented.

## Draft destination adapters

E1.3 owns all five strict draft kinds: commander/task text, question, runtime_decision and approval. Its [structured answer contract](coding-plans/e1-3.md#structured-answer-contract) binds payload fields, size limits, source versions, pending-attempt identity and canonical acknowledgement before E7.3 consumes them. The text-only Draft/afterAcknowledgement example does not implement answer forms. These are saved answer fields and pending attempt IDs, not new answer APIs. Each source adapter supplies its existing validation/maximum payload and submission/expected-version semantics. WorkQuestionPanel, RuntimeDecisionPanel and canonical approval UI continue to own governed submission. Unauthorized/expired/resolved destinations retain or purge sensitive local draft under existing permission policy but never replay an answer. Test same-company different-user denial, stale expected version, unmount/reload, duplicate reply and revoked access at submit.

Checkpoint content and a text/answer draft are not stored twice. E5 field data lives in the checkpoint; its pending `clientActionId`/`clientSubmissionId` mapping is separate recovery metadata. E1.3 does not treat generated form data as text and clear it after an unrelated Commander reply.

## Artifact and durable-follow-up qualification decisions
