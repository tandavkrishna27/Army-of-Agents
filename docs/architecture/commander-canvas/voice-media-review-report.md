## Findings (severity-ranked)

**No Critical/High.**

- **[MEDIUM-1 — legacy Secrets exemption, resolver-layer residual] Purpose-binding is enforced at the broker and keyed to consumer type; the underlying resolver still exempts system/plugin/no-configPath callers.** Verified: `shouldEnforceSecretBinding` returns `false` for those consumer types (`secrets.ts:211-221`), and binding is matched `targetType == consumerType` (`:444`). So a voice-media connection secret's purpose binding is enforced **only** when the caller presents the non-exempt `provider_connection` consumer type; any caller using `system`/`plugin`/no-`configPath` would resolve the secret with **no** binding check. The plan's control is broker-layer ("broker must explicitly require an existing matching binding … generic system/plugin consumer is rejected") and correctly refuses to weaken the legacy exemptions — but that leaves the guarantee dependent on the broker being the **sole** resolver of connection-bound secretRefs and on it self-classifying correctly. **Recommendation for security acceptance:** additionally enforce binding at `resolveSecretValue` for any secretRef that HAS a `provider_connection` binding (target-presence enforcement, independent of consumer type), or prove no non-broker consumer can resolve a connection-bound secretRef; state that requirement explicitly rather than relying on broker discipline alone. *Evidence:* voice-media-policy.md §"Credential and source bindings"; `secrets.ts:210-223,444`.

- **[MEDIUM-2 — durable budget reservation is a new, cross-cutting primitive] The budget-admission guarantee depends on an atomic reservation primitive that does not exist at base.** Verified: `getInvocationBlock` is a hard-stop check without reservation (`budgets.ts:345`) and `budget-hooks.ts` is an in-process `EventEmitter` (`:1,14,40-45`), not durable cross-worker revocation. The plan correctly names this ("Existing getInvocationBlock alone does not establish reservation … the budget owner must bind atomic capacity/reservation accounting … the local emitter is only an optimization") and assigns it to "E3.1/E8.1 budget integration" + the budget owner. But it is a **new budget-owner deliverable**, cross-cutting (concurrent-admission safety, durable session-stop consumption, hard-stop under delayed provider usage all depend on it), and the load-bearing budget gate. **Recommendation:** ensure the durable reservation/atomic-capacity primitive is owned and scheduled as a budget-owner qualification (not treated as voice-local), and that "no path enabled until reservation + durable session-stop consumption exist" is a hard gate. *Evidence:* voice-media-policy.md §"Budget, revocation and retention"; `budgets.ts:345`, `budget-hooks.ts`.

- **[LOW-1 — session single-owner enforcement mechanism unspecified] `universe_voice_sessions`'s "one nonterminal voice owner per (companyId, userId) across tabs" invariant lacks a concrete enforcement mechanism.** The record proposes unique `(companyId, userId, startRequestId)` + a single-nonterminal-owner rule + a takeover protocol, but does not specify the constraint that enforces single ownership (e.g., a partial unique index `WHERE state <> terminal`), as E1.2 did for `openedOrdinal`. It is deferred to "reconcile exact unique keys with the existing E2/E8 producers in the bounded plan." Recommend specifying the exact partial-unique/enforcement mechanism before coding so the invariant is not left to implementation. *Evidence:* voice-media-policy.md §"Connection and outcome contract".

- **[LIMITATION — not a finding against the plan] Vendor-API currency is unverified by this review.** The evidence packet is dated Sept 12, 2026 and its vendor facts (gpt-realtime-2.1, GPT-Live semantics, gemini-3.1-flash-live-preview synchronous tools, GPT Image 2.5, Veo 3.1, ElevenLabs 2-year default retention, and the **Sora 2 / Videos API shutdown on Sept 24, 2026**) are beyond my January 2026 training cutoff; per the review constraints I opened no provider sessions or docs. I therefore did **not** independently certify any live vendor deprecation/supported-operation/retention claim. The plan handles this correctly — it labels everything "Documentation research only … Recheck exact model availability, account entitlement, region, price and deprecation at qualification," excludes Sora conservatively (fail-safe), and treats vendor terms as unqualified — so the review's inability to certify vendor state does not undermine the plan; it *is* the plan's own qualification gate. **Action for TK:** every vendor fact (especially the Sora shutdown date, each model's supported operations, and per-provider retention/ZDR/region terms) must be re-verified against live official docs at qualification before any account enablement or spend.
