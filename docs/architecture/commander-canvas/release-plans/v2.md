# Universe V2 — proposed later release plan

**Status:** Later-speech allocation accepted; planning permitted now. Implementation is barred until all agreed V1 scope is complete and verified. Multi-screen remains a deferred candidate, not committed V2 scope. See the [acceptance record](README.md).

## Proposed scope from the existing register

| Epic | Slice | Planned outcome | Required foundation |
|---|---|---|---|
| E3 Voice | [E3.4](../slice-plans/e3-4.md) | Separate speech-recognition/synthesis pipelines and local speech | Completed V1, common voice controls/continuity, canonical Commander outcomes, scoped providers/preferences and mode-specific qualification |

The slice has three increments: qualify/build the separate pipeline, qualify/build the local runtime, then perform integrated V2 regression and rollout. Actual providers, supported local hardware/models and installation policy must be bound by qualification; this draft invents none of them. Local speech does not imply offline task execution.

## Deferred feature, outside committed slice count

[Multi-screen Universe](../master-scope.md#multi-screen-universe--deferred-after-desktop-app) is recorded for reconsideration **after the desktop app**, as the user requested. V2 is tentative, not guaranteed. Do not assign an executable slice until this separate design is groomed.

That later design must choose linked viewports versus one continuous canvas; browser/desktop window behavior; panel transfer and duplicate views; one voice owner; permission/session synchronization; monitor disconnect recovery; keyboard focus and independent window geometry. A second browser window is a proposal, not an accepted implementation. This sequencing choice does not assert that browser multi-window technically requires a desktop app.

Broader Accounts and Access, communications, meetings/calendar/email and full backend apps remain separate workstreams. Their relevant interfaces constrain Universe, but this release plan does not silently absorb them into V2.

## V2 exit criteria

- [ ] V1 acceptance is recorded before the first V2 runtime change.
- [ ] E3.4 capability/hardware/credential/latency and recovery qualification is complete, with explicit availability boundaries.
- [ ] Recognition corrections, interruption and reconnect preserve one canonical request and originating conversation.
- [ ] New modes reuse existing settings scopes and independent chat/blob/captions; V1 realtime modes pass regression.
- [ ] Apply the E8.2 release evidence checklist to this new integrated revision, including security, accessibility, full checks and rollback. This is reuse of the gate, not reassignment of E8.2 to V2.
- [ ] Any added feature, including multi-screen, has a reviewed scope amendment and its own detailed slice plan before coding.
