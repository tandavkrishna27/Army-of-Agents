Pinned existing `CommanderInput` and `InternalAgentPanel` manage input references; reuse their attachment validation and canonical clients. `issuesApi.addComment` and `addCommentWithAttachments` already accept clientSubmissionId. Commander chat accepts message max 10,000 chars and five attachment asset IDs; draft validation must honor the destination's existing validator, not broaden it.

```ts
export type Destination = {kind:'commander'|'task'|'question'|'runtime_decision'|'approval';id:string};
// Text-only helper: never used for question/runtime_decision/approval payloads.
export type Draft = {revision:number;text:string;attachmentAssetIds:string[]};
export type SentSnapshot = Draft & {clientSubmissionId:string};
export function afterAcknowledgement(current:Draft, sent:SentSnapshot):Draft {
  const unchanged = current.revision===sent.revision && current.text===sent.text &&
    JSON.stringify(current.attachmentAssetIds)===JSON.stringify(sent.attachmentAssetIds);
  return unchanged ? {...current,text:'',attachmentAssetIds:[]} : current;
}
```

This proposed pure function changes local fields only; the server draft clear is a separate CAS patch after durable ack. Scope key is company/user/conversation/destination-kind/destination-id, never panel index or display title. `useUniverseDraft(scope,destination)` exposes `{draft,status,error,patch,submitSnapshot,acknowledge}`; `submitSnapshot` allocates and returns the immutable sent snapshot but does not execute a request by itself.

## Structured answer contract

E1.3 owns all five destinations. Add strict discriminated schemas to `packages/shared/src/validators/universe.ts` and source adapter logic to `server/src/services/universe-drafts.ts`; E7.3 consumes these rather than extending an untyped text draft. Proposed payload shape:

```ts
export type DraftPayload =
  | {kind:'commander'|'task';text:string;attachmentAssetIds:string[]}
  | {kind:'question';expectedVersion:number;text:string;selectedValues:string[]}
  | {kind:'runtime_decision';expectedSourceRevision:number;answer:
       {kind:'permission';decision:RuntimePermissionDecision|null} |
       {kind:'work_question';fields:Record<string,unknown>}}
  | {kind:'approval';observedUpdatedAt:string;decision:'approve'|'reject'|null;decisionNote:string};
export type RuntimePermissionDecision =
  Extract<RuntimeDecisionAnswerInput,{kind:'permission'}>['decision'];
export type PendingAttempt={attemptId:string;draftRevision:number;payloadHash:string;
  clientSubmissionId?:string;idempotencyKey?:string;state:'pending'|'unknown'|'acknowledged'};
```

Derive the permission type from the existing exported `RuntimeDecisionAnswerInput` in `packages/shared/src/validators/hub.ts`; do not create a new enum. Runtime work-question fields require the canonical question's declared schema and option membership; the transport record type is not authorization for arbitrary fields. Partial drafts may be empty; final answers must pass the existing strict source validator before explicit submission.

| Destination | Editable bound and source adapter | Frozen submission and recovery |
|---|---|---|
| commander/task | Existing destination text/attachment validator; draft example above remains text-only | Canonical clientSubmissionId; freeze entire text/refs/destination; E2.2 or task's read-only receipt lookup |
| question | text ≤8,000, at most 20 selected values ≤500 chars, nonnegative expectedVersion; enforce source option membership. Based on `workQuestionAnswerSchema` / `answerWorkQuestionSchema` in `packages/shared/src/work-questions.ts` | Explicit Send builds `{answer:{text?,selectedValues?},expectedVersion,idempotencyKey}`; allocate one ≤200-character key per attempt and retain it across observation, never answer from restore |
| runtime_decision | expectedSourceRevision nonnegative; permission selection from canonical enum or work-question form fields strictly validated against its current source schema | Rehydrate canonical source and its current nonce on explicit submit through existing RuntimeDecisionPanel; nonce/credentials never saved in the draft. Preserve frozen expectedSourceRevision + idempotencyKey; stale source requires review, not an automatic rebase/reply |
| approval | approve/reject or empty selection, bounded decisionNote ≤8,000 (proposed draft limit), observedUpdatedAt from canonical approval | Existing approve/reject client receives `resolveApprovalSchema` body; selection chooses the existing route. observedUpdatedAt is a review-staleness check, NOT invented server CAS. No clientSubmissionId/idempotency support is assumed for approval; timeout becomes unknown, then read canonical approval before another deliberate action |

Cap serialized payload at 32 KiB and pending metadata at 2 KiB (qualification bounds), including nesting/field limits for source-defined forms. Strictly match stored kind to the authorized destination. The server resolves every destination through its canonical owner and current capabilities, never merely conversation membership. Source version/permission changes mark the draft stale/unavailable; retain a protected local candidate only under the existing permission/retention policy, without revealing it after revocation.

On acknowledgement clear by CAS only when destination, draftRevision and canonical payload hash all equal the sent snapshot. Text helper `afterAcknowledgement` never clears a structured answer or E5 checkpoint. New edits survive old acknowledgements. Persist PendingAttempt before Send where policy permits; record canonical receipt/result separately. An attemptId is local correlation and cannot substitute for a source's idempotency key or grant retry authority.

Within E1.3/1 add table/schema/auth tests for every kind, malformed form/unknown enum, byte limits and same-company other-user denial. Within E1.3/2 add changed-answer-during-Send, stale expectedVersion/sourceRevision, approval changed before Send, nonce rotation (not persisted), timeout→canonical read, duplicate callback, and reload with zero answer POSTs. E7.3 answer-form integration waits for these contracts/tests; no V1 kind is deferred.

## E1.3/1 — Draft storage

- [ ] Add unique scoped destination row with revision, strict discriminated DraftPayload JSON, separately bounded PendingAttempt metadata and updatedAt; add its company/owner checks and exports and generated migration. Use GET/PATCH `/api/companies/:companyId/universe/conversations/:conversationId/drafts/:destinationKind/:destinationId`; validate conversation and task membership/permission separately. No client userId field is accepted.
- [ ] Persist edits with expectedRevision and the per-kind payload validators below (text/attachments for commander/task only). On revision conflict retain both versions; do not concatenate automatically. Draft text may be private even when its task is shared. Foreign destination IDs must not reveal existence.
- [ ] Reuse validated asset references from composer upload; unresolved/failed attachments remain visible pending items and cannot silently attach to a different task. Cancel upload on destination/account switch or retain it under its originating draft key.
- [ ] Keep geometry out of draft rows. Close, minimize and maximize cannot clear a draft. Reset appearance/layout cannot delete draft data. Local offline caching is separately policy-gated; default durable store is the authenticated service, not unscoped localStorage.
- [ ] Test all pairs of company/user/conversation/destination for isolation using real DB fixtures; concurrent revisions, deleted task, revoked asset and failed-save recovery. Use the migrated Postgres harness from E1.2 and explicit auth middleware integration, not only service mocks.

## E1.3/2 — Submission acknowledgement and uncertain outcome

- [ ] For Commander/task Send only, freeze text, refs and destination, allocate clientSubmissionId once, and call the existing destination client. Later selection changes cannot retarget this submission. Prevent duplicate local presses while the same snapshot is pending; still rely on those canonical message clients' idempotency. Question/runtime answer adapters freeze their structured payload/source revision and allocate the supported source idempotencyKey instead. Approval uses only its existing explicit approve/reject route and local attempt correlation, with no invented server idempotency/CAS; uncertain result stays unknown until canonical observation.
- [ ] Clear only the sent snapshot after durable acknowledgement. If the user typed more while sending, retain the newer draft. Add these concrete pure tests:

```ts
it('keeps text typed after Send', () => {
  const sent={revision:4,text:'first',attachmentAssetIds:[],clientSubmissionId:'s1'};
  const current={revision:5,text:'second',attachmentAssetIds:[]};
  expect(afterAcknowledgement(current,sent)).toEqual(current);
});
it('clears exactly the acknowledged snapshot', () => {
  const sent={revision:4,text:'first',attachmentAssetIds:[],clientSubmissionId:'s1'};
  expect(afterAcknowledgement(sent,sent).text).toBe('');
});
```

- [ ] On timeout/reload, mark pending outcome and use E2.2 Commander lookup or the existing task comment idempotency identity/read path. Do not post again on reconnect. If task lookup cannot conclusively identify the submission, retain unknown and expose deliberate retry only after explaining possible prior acceptance; add a read-only task outcome binding before calling automatic recovery complete.
- [ ] E2.4 maps reply controls to task destinations and E1.5 maps compact/expanded chat to one Commander draft. Verify switching between two task composers during pending sends keeps each reply in its original thread.
