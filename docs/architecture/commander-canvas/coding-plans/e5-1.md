# E5.1 — Reviewed interactive blocks implementation plan

> **For agentic workers:** Use superpowers:executing-plans only after TK approves the reviewed implementation packet. No implementation or runtime verification is authorized by this plan.

**Goal:** Render schema-validated charts, tables, forms and calculators with local interaction, bounded Commander context and separately governed actions.

**Architecture:** Deployment-controlled React registry interprets untrusted data. E1.2 owns durable panel checkpoint CAS; E5.1 owns its validated block payload, and E1.3 retains pending submission metadata separately. Canonical references resolve via E2.1, and explicit action intent enters E2.2. Composition JSON cannot load code, create grants or register a privileged renderer.

**Tech stack:** Existing React/TypeScript/Zod, shared viewers and canonical APIs; no expression-evaluation or remote component package.

**Spec:** [E5.1 outline](../slice-plans/e5-1.md), [panel contract](../panel-contract.md), [master scope](../master-scope.md), [U04/U09/U10](../ui-review-decisions.md), [settings](../settings-contract.md). Both original increments are V1.

Define the data schema first. All objects strict, plain data, no `html`, script, expression, import path, event handler or model-controlled URL field:

```ts
import { z } from "zod";
const label = z.string().min(1).max(120);
const cell = z.union([z.string().max(2000), z.number().finite(), z.boolean(), z.null()]);
const ref = z.discriminatedUnion("kind", [
  z.object({ kind: z.literal("artifact_version"), artifactId: z.string().uuid(), versionId: z.string().uuid() }).strict(),
  z.object({ kind: z.literal("task"), taskId: z.string().uuid() }).strict(),
]);
const common = { id: z.string().uuid(), version: z.literal(1), title: label };
export const reviewedBlockSchema = z.discriminatedUnion("type", [
  z.object({ ...common, type: z.literal("table"), columns: z.array(label).min(1).max(50),
    rows: z.array(z.array(cell).max(50)).max(1000) }).strict(),
  z.object({ ...common, type: z.literal("chart"), chart: z.enum(["bar", "line"]),
    xLabel: label, yLabel: label, points: z.array(z.object({
      x: label, y: z.number().finite(),
    }).strict()).max(1000) }).strict(),
  z.object({ ...common, type: z.literal("calculator"), operation: z.literal("sum_products"),
    terms: z.array(z.object({ id: z.string().uuid(), label,
      quantity: z.number().finite().min(0).max(1_000_000),
      unitCost: z.number().finite().min(0).max(1_000_000),
    }).strict()).min(1).max(100) }).strict(),
  z.object({ ...common, type: z.literal("form"), fields: z.array(z.object({
    id: z.string().uuid(), label, kind: z.enum(["text", "number", "boolean"]),
    required: z.boolean(),
  }).strict()).max(30), action: z.literal("commander.request") }).strict(),
]);
export const reviewedCompositionSchema = z.object({
  schemaVersion: z.literal(1), title: label,
  blocks: z.array(reviewedBlockSchema).min(1).max(12),
  references: z.array(ref).max(20),
}).strict();
export type ReviewedComposition = z.infer<typeof reviewedCompositionSchema>;
export type ReviewedBlock = z.infer<typeof reviewedBlockSchema>;
```

Add refinements for unique block/field/term IDs and table row width exactly columns length; enforce serialized UTF-8 composition size ≤256 KiB before parsing, then per-array bounds. Source references are selectors/data hints; they grant no access. Task references point to live tasks, while artifact references require an exact immutable version. Export `BlockReference = z.infer<typeof ref>` and adapt explicitly to E2.1's shared `UniverseReference`; never cast differing structures:

```ts
export function toUniverseReference(reference: BlockReference): UniverseReference {
  return reference.kind === "artifact_version"
    ? { kind: "artifact", id: reference.artifactId, versionId: reference.versionId }
    : { kind: "task", id: reference.taskId };
}
```

export function calculateSumProducts(
  terms: readonly { quantity: number; unitCost: number }[],
): number {
  const value = terms.reduce((sum, term) => sum + term.quantity * term.unitCost, 0);
  if (!Number.isFinite(value)) throw new Error("Result exceeds supported range");
  return value;
}

## E5.1/2 — State and action boundary

**Create:** `ui/src/components/universe/blocks/block-state.ts`, `block-context.ts`, `block-actions.ts`, `__tests__/block-actions.test.ts`, `tests/e2e/universe-reviewed-blocks.spec.ts`. **Modify:** E1.2 checkpoint payload-schema registration and E2.1 context resolver adapter; consume E1.3 pending-submission metadata and E2.2 request submission component. E1.2 owns new `universe_panel_checkpoints` migration/routes, not this slice. Do not add a block-specific task creation route.

```ts
export interface BlockCheckpoint {
  schemaVersion: 1; compositionVersionId: string; instanceId: string;
  revision: number; inputs: Record<string, string | number | boolean>;
  selectedRows: number[]; filters: Record<string, string>;
}
export interface BlockActionIntent {
  action: "commander.request"; clientActionId: string;
  instanceId: string; compositionVersionId: string; checkpointRevision: number;
  instruction: string;
}
export interface BlockActionPort {
  request(intent: BlockActionIntent): Promise<SubmissionOutcome>;
}
```

`BlockCheckpoint` above is the renderer-facing view model. E1.2 owns the durable envelope identity, revision/CAS and access; map `compositionVersionId` to that envelope's artifact version and `instanceId` to panel instance explicitly. Only `{inputs,selectedRows,filters}` is the E5-owned state payload, validated with the composition schema version. Do not write a second revision/identity authority inside JSON. E1.2's payload limit is 32 KiB including serialized state; payload-schema migrations preserve or retain a prior version. Block action sent-snapshot metadata in E1.3 references the accepted E1.2 checkpoint revision and does not copy mutable state into a second store.

`SubmissionOutcome` is imported from E2.2's shared API contract: `{clientSubmissionId,observedAt,state:'unknown'|'accepted'|'running'|'succeeded'|'failed',userMessageId?,replyMessageId?,runId?,reason?}`. No parallel outcome union is introduced. Approval/denial is domain UI state associated with the canonical outcome, not an extra invented turn state. `BlockActionPort` is a proposed UI adapter to that authority; map its stable clientActionId to one stored E2.2 clientSubmissionId. Only the host constructs it after actual user action. Server resolver reloads composition/reference permissions and selected checkpoint before dispatch. Model form label/content cannot authorize its own submission; default action asks Commander through existing conversation/send permission and approval path. Further named task/artifact actions require explicit schema additions plus canonical route/RBAC tests, never `operation:string` arbitrary dispatch.
