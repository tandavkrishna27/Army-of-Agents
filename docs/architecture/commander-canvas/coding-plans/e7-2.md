> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans only after explicit implementation approval. Keep blocked producer bindings blocked until evidence closes them.

**Proposed contracts (define before consumers):**

```ts
export interface FollowupRuleInput {
  source: { kind: "issue" | "routine_run"; id: string };
  terminal: "completed" | "failed";
  targetRoutineId: string;
  expiresAt: string;
  maximumFirings: number;
}
export interface FollowupRule {
  id: string; companyId: string; createdByUserId: string | null;
  createdByAgentId: string | null; revision: number;
  state: "active" | "paused" | "revoked" | "exhausted";
  input: FollowupRuleInput; authorizedAt: string;
}
export interface FollowupOccurrence {
  id: string; ruleId: string; companyId: string; sourceTransitionId: string;
  state: "pending" | "admitted" | "blocked" | "cancelled";
  targetRunId: string | null; reason: string | null;
}
export type FollowupBinding = {
  kind: "issue" | "routine_run"; sourceId: string; companyId: string;
  transitionId: string; terminal: "completed" | "failed"; committedAt: string;
};
```

`routineFollowupService(db)` exposes `create(context,input,invocationId):Promise<FollowupRule>`, `setState(context,id,baseRevision,state:"paused"|"active"|"revoked"):Promise<FollowupRule>`, `list(context):Promise<FollowupRule[]>`, and internal `recordTerminalTransition(tx,binding):Promise<void>`. `context` is the trusted E7.1 routine action identity, not a model-created actor. Validators are strict: UUID references, ISO timezone-bearing expiresAt, maximumFirings integer 1–25, source/target same company, expiry after now and at most 30 days. These proposed bounds keep standing rules inspectable; increasing either requires explicit policy review, not learning from repeated use. Default one firing and seven days only when plainly displayed in the conversational proposal; recurring source rules require explicit bounded request. No recursion: reject a follow-up targeting its own source routine and reject creation of a cycle in the bounded source→target rule graph. Graph traversal cap 100 nodes; exceeding it refuses creation with an actionable scope-too-large response.

Routes under `/api`: GET/POST `/companies/:companyId/routine-followups`, PATCH `/companies/:companyId/routine-followups/:id` with `{baseRevision,state}`. They use shared E7.1 routine permission checks plus current source visibility. UI/model cannot set company, actor, authorizedAt, transition ID or counters. Permission includes managing target assignment and reading the source; same-company alone is insufficient. Logged actions: `routine_followup.created|paused|resumed|revoked`, with IDs/revisions/counts, no source body or provider credentials. Resuming must reauthorize and never retroactively execute an event that occurred while paused unless explicitly approved as a new intent.

**Schema:** `routine_followup_rules`: id/company FK, creator user/agent nullable with exactly one identity, sourceKind/sourceId, targetRoutineId, triggerTerminal, explicit authorization receipt/invocation reference, authorizedAt/expiresAt, maximumFirings/firingCount, revision/state, timestamps. Unique original invocation+actor+company; hash-compare body on replay. `routine_terminal_transitions`: id, companyId, sourceKind/sourceId, authoritative source revision/token, terminal, committedAt; unique `(companyId,sourceKind,sourceId,sourceRevision)`. `routine_followup_occurrences`: id/companyId/ruleId/sourceTransitionId, state/targetRunId/reason, attempts/nextAttemptAt, timestamps; unique `(companyId,ruleId,sourceTransitionId)`. Foreign-key/company consistency uses composite keys or service transaction checks validated by cross-tenant fixtures; do not treat a UUID as scoped authority.

**Admission state machine:** Under company→target routine→rule→occurrence lock order, recheck rule state/expiry/firing cap and source/target permissions. Reserve one firing for a pending occurrence, then invoke canonical E7.1 admission with key `followup:<occurrence UUID>`. Persist target run ID and `admitted` in a transaction-safe receipt linkage; if network/worker delivery is unknown, read existing run by key before any second request. Reserve count and canonical admission must be atomic or recoverable through that receipt; losing a reserved count must not permanently block a legitimate occurrence. Canonical run state proves whether a Task exists; successful external effect is never repeated because a UI event was missed.

Use fixed `source:"api"` for every follow-up admission/reconciliation, since routine run dedupe includes source as well as routine/trigger/key. Store and inspect the canonical run's `issue_created|coalesced|skipped|failed|completed` status separately from occurrence `admitted`; a failed or skipped routine receipt must not be displayed as successful follow-up work. Activity is inserted through existing `insertActivityLog(tx,input)` and only published after commit. Tests count both receipt and execution Task/wakeup; a single failed receipt is not evidence of a successfully executed effect.

Proposed drain bounds: 100 occurrences per pass, one admission per locked occurrence, retry transient DB/service failures after 5s/30s/120s/600s/1800s then block for an owner decision, deterministic injected clock. Do not retry permission denial, revoked source, expired rule, budget hard stop, unsupported environment or external unknown outcome as temporary. A blocked budget item may be explicitly resumed after policy changes; it is not auto-promoted into authorization. Terminal marker/receipt retention lasts at least through active rule expiry plus 30 days; purge only after no active rule/receipt references, preserve minimum audit retention required by company policy. Default policy cannot delete the only deduplication evidence for still-retryable work.

## UI, settings, rollback and self-review

Follow-up list/loading/error/empty uses canonical authorized queries; stale offline data labeled stale, mutation disabled until authority confirmed. Pending/blocked/revoked/expired/admitted/completed are distinct. Layout movement, surface close and silent announcements do not revoke standing work. Explicit Pause/Resume/Revoke are logged canonical actions. E8 `attentionPreviews`, `soundEffects`, `spokenAnnouncements` change presentation only; E7.3 shared policy controls interruption. Keyboard/touch can open source Task/routine, narrow view fits available width, reduced motion gives immediate state changes; never use flashing or pan/zoom as completion evidence.

Migration is additive and does not infer follow-up rules from historical events, attendance, comments, repeated actions or existing notification preferences. New terminal markers begin at cutover; no synthetic historical trigger. Drain feature-disable leaves rules/occurrences/receipts intact; stop claims, allow canonical admitted work to retain normal semantics, and mark paused delivery. Rollback must keep terminal capture if pending rules still rely on it, or explicitly pause those rules and record a cutover gap; silently resuming after an unrecorded gap is forbidden. Old versions may ignore new tables but cannot safely resume pending rules until upgraded reconciliation accounts for every receipt. No schema drops.

**Self-review:** Both original increments include explicit authority, durable correlation, current reauthorization and recovery. Source replay capability is acknowledged without treating best-effort append as transactional delivery. Important unresolved work is terminal owner coverage and E7.1 transaction/admission binding; qualification has inputs, concrete failure points, expected evidence, reviewers and affected consumers. No real runtime/provider/DB tests ran here; readiness remains conditional.
