## Outcome

The `job-approval-bridge` makes a DISTRIBUTED attempt call the EXISTING product-approval / runtime-decision / completion authorities EXACTLY ONCE. The SERVER creates the aggregate (through the same `approvalService` / `agentRuntimeDecisionService`, with the source revision + nonce + digest + version + TTL + default those services already stamp), writes a JOB-005 projection RECEIPT linking that EXISTING aggregate to the attempt, and queues ONLY the E1 result control (`product_approval_result` / `runtime_decision_result`). It invents no approval/policy engine, no worker-created policy, no approval-UI change, and holds no managed compute while parked. **Flag-off leaves every current path byte-unchanged** — every entrypoint throws `JobApprovalBridgeDisabledError` before any DB or legacy effect.

## Reuse-table-vs-new-table decision — **reuse `job_projection_receipts` (+ `aggregate_kind`)**

Per the ticket's explicit "use the JOB-005 projection-receipt repository" and the schema's own reserved `status='pending'` for "a later multi-step projection (JOB-011)". A dedicated `job_governance_projections` table would duplicate the exact idempotency ledger the ticket says to reuse and require a second RLS pair. Instead the existing table gained ONE nullable discriminator column (`aggregate_kind`) and a widened `projection_kind` CHECK; the JOB-005 `attempt_started`/`attempt_terminal` rows stay valid (nullable column, superset CHECK).

## THE load-bearing correctness invariant — receipt fast-path BEFORE the authority create

`approvalService.create` (`approvals.ts:248`) has **NO native dedup** — a plain `INSERT ... RETURNING`. On a replay the receipt identity-unique `(organization_id, company_id, projection_kind, source_identity)` is the ONLY thing stopping a duplicate approval. So `openGovernedDecision` does a receipt **fast-path lookup BEFORE** driving the authority (mirroring JOB-010's `findIdempotentReplay` before the non-idempotent `issueService.checkout`): if a receipt for this source identity already exists, it returns the ALREADY-linked aggregate (`status: "replayed"`) WITHOUT a second create. The parity matrix proves it for **both** paths: two `openGovernedDecision` calls with the same `idempotencyKey`/source identity → the aggregate row count stays **1** and the receipt count stays **1** (task_run runtime decision + crew_run product approval). The runtime path is doubly idempotent (the aggregate's native `sourceUniqueKey` upsert); the product path relies SOLELY on the receipt.

## `park_run` semantics (end attempt / release compute / parked — NO auto-retry) — **CORRECTED**

No managed compute is held while parked (CAV-001). **Grounded parity (code-is-truth):** the legacy runtime-decision `park_run` timeout is `fallbackPolicyOutcome` (`agent-runtime-decisions.ts:690`), which returns `status:'cancelled', cancelsRun:true, parked:true` — legacy park **CANCELS the run and does NOT auto-retry**. `parkRun` mirrors this EXACTLY: in ONE tenant tx it calls `requestCancellation` ONLY — with a fenced worker this marks the job/attempt `cancel_requested` and queues ONE `cancel` control (the worker is told to stop → compute released); with no fenced worker it finalizes the attempt+job `cancelled` directly and releases the JOB-007 capacity slot. It returns `{ status, parked: true }`.

**It does NOT reap or mint attempt N+1.** `requestCancellation` marks the job `cancel_requested`, which routes the reaper down the CANCEL branch (`reapExpiredLeases`: `cancelling = job.status==='cancel_requested'` → `finalizeJob('cancelled')`, never `allocateRetry`) — so a reap step could NEVER resume THIS job, and its `retried` count would only surface OTHER org jobs' retries (wrong scope AND wrong kind). The ticket's "resume through a NEW fence" is satisfied STRUCTURALLY: the parked attempt's fence is driven terminal, so any LATER resumption — when a human answers the parked work-question through the future continuation flow (out of JOB-011 scope) — necessarily rides a FRESH fence, and `guardActiveFence` rejects any late control on the dead fence. Proven by two honest cases: park of a fenced active attempt → `cancel_requested` + exactly ONE queued `cancel` control (`parked:true`); and `[park_run] does not mint a retry attempt` → the REAL `parkRun` leaves the `job_attempts` count at **1** (no N+1) and the job `cancel_requested`.

## Worker-cannot-create/approve/override — STRUCTURAL

The bridge is a control-plane module invoked from dispatch/projection paths only; **no worker-facing create/approve route exists** (matrix asserts `worker-control.ts` never references the bridge, and the bridge surface is exactly `{isEnabled, openGovernedDecision, resolveGovernedDecision, parkRun}` — no `workerCreate`/`override`). The three new repo mutators (`recordGovernedProjection` / `markGovernedProjectionApplied` / `queueGovernedControlCommand`) each `guardActiveFence` FIRST (a stale/old-generation fence throws before any effect) and are classified in the JOB-004 fence-surface contract's `EXPECTED_UNGUARDED` (server-only, outside the worker-fenced closed set). The E1 control body is validated by the frozen `controlCommandV1Schema` (audience `control_channel`) before it is queued; the worker only ACKs. `acceptEvent`'s `runtime_decision_requested` remains an OBSERVATION (creates 0 aggregates).

## Fail-before-effect

The minted runtime-decision request is parsed through the frozen `runtimeDecisionRequestV1Schema.superRefine` BEFORE any DB write: an invalid/missing/multiple `continue_with_default` default and a forbidden persistent `allow_always` timeout grant (omitted from `PERMISSION_DEFAULT_DECISIONS`) both throw → the matrix asserts **0 aggregates, 0 receipts, 0 controls**. The active-rollback case forces the receipt INSERT to fail mid-tenant-tx → the whole transaction rolls back → **0 aggregates, 0 receipts**, and the after-commit live poke fired **0 times** (vs exactly once on commit).

## Deviations from the plan

- **`park_run` resume proof — CORRECTED by the independent review.** The original authoring called `reapExpiredLeases` inside `parkRun` and returned a `retriedAttemptNumber`, claiming it "resumes through a NEW fence / mints attempt N+1". That was WRONG: `requestCancellation` marks the job `cancel_requested`, which routes the reaper down the cancel branch (`finalizeJob('cancelled')`, never `allocateRetry`), so the reap can NEVER resume THIS job — and `retried` reported OTHER org jobs' retry counts (wrong scope + wrong kind). The reap call is REMOVED; `parkRun` now returns `{ status, parked: true }`, exact parity with the legacy `park_run` timeout (`agent-runtime-decisions.ts:690` → `cancelsRun:true, parked:true`, no auto-retry). Resumption via a fresh fence is a FUTURE continuation-flow concern (out of JOB-011 scope). The old, misleading `[park_run → new fence]` test (which bypassed `parkRun` entirely and drove `reapExpiredLeases` directly on a hand-abandoned attempt) is replaced by an honest `[park_run] does not mint a retry attempt` test driving the REAL `parkRun`.
- **E1 request `requestId`.** The server-minted decision has no `requestId` column, so the aggregate `id` IS the request identity: the E1 `runtime_decision_result` echoes `requestId = decision.id`, `requestDigest = promptHash`, and the row's nonce/sourceRevision/expiresAt/timeoutPolicy 1:1, so `matchRuntimeDecisionResultToRequestV1` binds it (proven in the matrix). Fail-before-effect validation runs on a placeholder-`requestId` request (the `.superRefine` default/options rules are `requestId`-independent).
- **After-commit publication.** The runtime/approval services emit their hub items IN-tx (DB writes that roll back correctly). The bridge's OWN after-commit sink stages a generic `publishLiveEvent` poke (proven fire-once-on-commit / zero-on-rollback). Deferring the services' internal hub emits to the sink is left for the JOB-013 first-class `fn(repos,{tx,afterCommit})` context (plan risk #8).
- **`runCanceller` wiring.** The plan suggested injecting `agentRuntimeDecisionService(tx,{runCanceller: requestCancellation})` so a `park_run` timeout in `expireDuePrompts` ends the distributed attempt. `parkRun` instead calls `repos.jobControl.requestCancellation` DIRECTLY (end attempt/release compute) + `reapExpiredLeases` — which satisfies the ticket's park semantics without routing through the runtime-decision timeout sweep. `expireDuePrompts` is a scheduler-driven path, not a bridge entrypoint; wiring the distributed `runCanceller` into that sweep is a scheduler-integration concern deferred with the proactive-scan scheduler. The bridge constructs the runtime-decision service without the injection because its create/resolve moments never trigger timeout expiry.

## Independent check (adversarial review, 2026-08-14)

A distinct adversarial pass over the staged JOB-011 implementation confirmed **4** real defects; all are FIXED in the working tree (logic + one read-only repo method + regression tests; no schema/migration change; keystone + fence-surface + migration-idempotency stay green; `tsc` clean). Each fix was proven fail-first (back out → new test fails → restore).

1. **[HIGH] `parkRun` terminally cancels but FALSELY claimed auto-resume.** The reaper cancel-vs-retry branches are mutually exclusive: `requestCancellation` marks the job `cancel_requested` → the reaper's cancel branch, so `parkRun`'s `reapExpiredLeases` could never resume THIS job, and `retriedAttemptNumber = reaped.retried` reported OTHER jobs' retries. **Fix** (`job-approval-bridge.ts` `parkRun`, ~739): removed the `reapExpiredLeases` call; keep only `requestCancellation`; return `{ status, parked: true }`. `ParkRunOutcome.retriedAttemptNumber` → `parked: boolean`; removed the now-dead `baseBackoffMs`/`maxBackoffMs` from `ParkRunInput`. File-header + docstring rewritten to the grounded semantics (cite `agent-runtime-decisions.ts:690`). *Fail-first:* old outcome shape → `[park_run] does not mint a retry attempt` fails (`out.parked` undefined).

2. **[HIGH] product-approval create TOCTOU.** `openGovernedDecision`'s product path did an UNLOCKED `findGovernedReceipt` then `approvalService.create` (NO native dedup), guarding the lease only LATER in `recordGovernedProjection`. Two concurrent same-`idempotencyKey` creates both pass the fast-path → **2 approvals, 1 receipt** (the orphaned 2nd is live + pending → a founder could approve it → duplicate `crew_dispatch`). **Fix:** added `JobControlRepository.lockActiveFence(input)` (`= guardActiveFence(input)`, read-only lease+attempt `FOR UPDATE`), and call it as the FIRST statement in the product `runInTenant` callback (`job-approval-bridge.ts` ~592), BEFORE `findGovernedReceipt`, so the 2nd caller blocks until the 1st commits its receipt then replays. *Fail-first (deterministic):* a side-transaction holds the lease `FOR UPDATE` while two concurrent creates run — without the lock both create before blocking at `recordGovernedProjection` (Set{'created'} → 2 approvals); with it, one creates + one replays (1 approval). (Naked `Promise.all` alone was NOT reliably fail-first: the 1st tx commits before the 2nd reads; the lease-lock barrier forces the overlap, held **250ms** — under the pool's 750ms `lock_timeout`.)

3. **[MEDIUM] `parkRun` docstring/header lied about auto-resume.** Folded into fix 1 — the header comment (~26) and `parkRun` docstring now state end/release/parked, no auto-retry, citing the legacy `fallbackPolicyOutcome`.

4. **[MEDIUM] runtime-decision resolve queues a DUPLICATE control on replay.** `resolveGovernedDecision`'s runtime path computed `const commandId = randomUUID()` every call; on an idempotent answer-replay (same `answerIdempotencyKey`) `answerPrompt` returns the already-answered row without throwing and `markGovernedProjectionApplied` is a no-op, but the fresh id defeats `queueGovernedControlCommand`'s `(org, lease, command id)` dedup → a SECOND `runtime_decision_result`. **Fix** (`job-approval-bridge.ts` ~672): `const commandId = row.id;` — the decision aggregate id is a stable UUID (one decision → one result control), so a replay dedups. *Fail-first:* restoring `randomUUID()` → `[replay] resolving the same runtime decision twice` fails (2 result rows). (The product resolve path is already safe — `approve()` throws on a non-pending status and rolls back.)

**Residual risk / notes.** The TOCTOU regression uses a lease-lock barrier + a 250ms hold (deterministic on embedded PG localhost, comfortably under the 750ms `lock_timeout`); on a much slower runner the hold could in principle expire before both callers block, which would only weaken the fail-first signal — the WITH-fix pass (1 approval) is guaranteed by `lockActiveFence` regardless of the hold. `lockActiveFence` is classified non-writer/guard-only in the fence-surface contract, consistent with the other control-plane governance methods.
