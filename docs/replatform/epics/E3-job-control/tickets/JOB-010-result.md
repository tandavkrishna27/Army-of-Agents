## Outcome

`admitAndSubmit(source, actor, idempotencyKey)` bridges EVERY authenticated execution source to its EXISTING admission/assignment authority and records ONE immutable distributed submission in the SAME authoritative tenant transaction. It is a parity/shadow bridge, not a cutover: **flag-off leaves every current path byte-unchanged** (the bridge refuses fail-closed and touches nothing). `task_run` — the ONLY frozen source that carries issue/run identity — reuses the as-built `issueService.checkout` engine, so a legacy heartbeat claim and a distributed claim for the same run converge on ONE winner and a different-run claim loses the atomic conditional UPDATE.

## Failure / rollback / release proof

- **Reject before job:** an unmet dependency / ownership conflict / stale-status makes `issueService.checkout` throw INSIDE the tenant tx → the whole tx rolls back BEFORE any `jobs` row exists (parity [1],[4],[4b],[5]).
- **Release on rollback (exactly once, no explicit release):** a forced pre-commit `jobs` INSERT failure aborts the tx → the checkout claim is un-done atomically (issue back to `todo`, `checkout_run_id` NULL) with nothing to release (parity [8a], after-commit rollback test).
- **No publication on rollback:** the deferred `issue.status_changed` publish is drained ONLY after the tx commits — the rollback test proves the spy fired **0 times**, and the success test proves it fired **exactly once** with the durable `(companyId, issueId, "in_progress")` (after-commit tests).
- **Explicit single-release:** `releaseTaskClaim` uses the run-guarded `issueService.release` — the owning run releases exactly once; a foreign run is rejected ("Only checkout run can release issue") (parity [8b], after-commit release test).
- **One winner / dedupe:** a concurrent two-run race resolves to exactly one winner and one job (parity [6]); a legacy `submit` and a bridge `admitAndSubmit` on the same composite dedupe to one job via `insertJobOnce` ON CONFLICT (parity [7]).

## Stable bridge-claim identity (no new authoritative column)

The legacy↔distributed link is the EXISTING `insertJobOnce` composite (`authenticatedSourceIdentity = sourceIdentity(source)`); for task_run that is `jobs.authenticatedSourceIdentity == issues.executionRunId`. No new assignment/capacity column is authoritative.

## Independent check + one confirmed fix applied

A 2-lane adversarial Workflow (parity-fidelity + correctness/concurrency). The central parity call — task_run drives checkout while crew_run/one_shot/commander/browser/service are admit-only (not driven) — was **verified correct**: the frozen source type gives non-task sources no `issueId`, the crew runner does its own execute-time checkout (runner.ts), and reconstructing an issue would be the forbidden "fabricated task identity". Two findings were **refuted**: the matrix's `capacity_claim_release_wakeup` "tautology" is the honest encoding of an explicit non-goal (JOB-007 owns capacity), and `release` not clearing `executionRunId` is pre-existing legacy behavior identical to the legacy release route (faithful parity, outside the diff).

**One confirmed defect (MEDIUM) — task_run replay re-ran checkout non-idempotently → FIXED.** `admitAndSubmit` drove `issueService.checkout` unconditionally for task_run BEFORE `submitJobWithinTenant` resolved the idempotent replay. On a same-run redelivery the checkout WHERE clause still matched (issue `in_progress`, `checkoutRunId==runId`), so the atomic UPDATE re-fired: `startedAt` was reset forward (corrupting recorded start time / run-duration) and a spurious `issue.status_changed` event was re-broadcast — while the submission half correctly returned `replayed:true`. The bridge advertises idempotent replay (via `idempotencyKey`) but the checkout side-effect was not idempotent. **FIX:** a write-free `findIdempotentReplay(repos, input)` (exported from `job-submission.ts`) runs INSIDE the authoritative tx BEFORE checkout for task_run; on a detected replay the bridge returns the already-committed submission WITHOUT re-driving checkout. The legacy checkout engine is untouched (parity preserved); only the bridge now honors its own idempotency contract. Regression: parity test **[2]** strengthened to assert `started_at`-stability across a replay (proven fail-first: with the fix disabled it fails `started_at 2026-…439Z ≠ …406Z`).

## Non-goals (respected)

No execution cutover; no new authoritative assignment/capacity store/column; no distributed capacity authority and no second capacity release engine (JOB-007 owns `admit/releaseAttemptCapacity` — the bridge releases only the ISSUE claim via `issueService.release`); no fabricated task identity for non-task sources (only `task_run` carries issue/run identity); no model/provider effect in shadow mode (commander_turn is inert — `aoa_app` holds only SELECT on `internal_agent_messages`, so `claimTurn` is out of the grant surface).
