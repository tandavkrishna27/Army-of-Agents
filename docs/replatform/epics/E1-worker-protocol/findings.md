## E1-F004 — PRT-003 local extension byte-sizer diverges from the E0 RFC-8785 canonical authority: `jobEnvelopeV1Schema` fails OPEN on non-canonicalizable extension values (floats, unsafe integers, lone surrogates)

- **Severity:** High (fail-open at a `.strict()` security-critical wire envelope; admits values the program's canonical/event pipeline cannot process).
- **Blocks gate:** No (epic gate). **Blocks PRT-003 approval:** Yes (reviewer disposition `changes_requested`).
- **Discovered during:** PRT-003 independent review (reviewed revision `d381a3a46f16f5ef05c26a0b8101be63509f927a`).
- **Context:** PRT-003 must bound each extension value at "≤16,384 **RFC-8785-canonical** UTF-8 bytes" (plan hardening amendment, [implementation-plan.md](implementation-plan.md) line 71). Because the shared `canonical-json.ts` is a PRT-004 deliverable, `job.ts` carries a small **self-contained** canonical serializer (`canonicalString`/`canonicalJson`/`canonicalByteLength`, lines ~161–196) used only to size extension values (the implementer's own Concern #1 / Deviation 1). The program pins "RFC-8785 canonical JSON" to the **frozen E0 implementation** `scripts/check-distributed-execution-foundation.mjs` (`canonicalizeJson`), and the amendment's PRT-004 clause (line 97) **explicitly enumerates** "lone surrogates, unsafe-integer boundary … `-0`" as the exact edge cases where the two canonicalizers must **not** diverge.
- **Evidence (independently reproduced against the reviewed revision):**
  - **In-subset agreement is perfect** — a 23-case battery (nested objects/arrays, multibyte `é`/astral emoji, combining NFD, every control-char escape, integers, `-0`, booleans, `null`, key-ordering variations, unicode keys) produced **byte-for-byte identical** canonical strings and byte counts to E0; the real-schema value byte-budget boundary matches E0's count exactly at 16,384 pass / 16,385 fail for ASCII **and** multibyte (`é`). So the sizer is correct for representable values.
  - **Out-of-subset DIVERGES on accept/reject.** E0 `canonicalizeJson` **rejects** floats ("float is not allowed"), unsafe integers ("unsafe integer is not allowed"), and lone/broken surrogates ("lone … surrogate in string"). The local `canonicalJson` **silently accepts** all of them (numbers via `String(value)` with only a `Number.isFinite` guard; strings emit surrogate code units verbatim, and `TextEncoder` then substitutes U+FFFD). The structure walk `addExtensionValueStructureIssues` only flags non-**finite** numbers, so floats, unsafe integers, and lone-surrogate strings pass unflagged.
  - **The divergence reaches the REAL `jobEnvelopeV1Schema`.** `jobEnvelopeV1Schema.safeParse(job)` **returns `success: true`** for a job whose extension value is `1.5`, `9007199254740992` (2⁵³), a lone-surrogate string `"\uD800"`, `{ rate: 0.25 }`, or `[9007199254740992]` — every one of which E0 declares non-canonicalizable. It also **propagates through `leaseOfferV1Schema`** (a lease offer whose nested job carries a float extension value is accepted).
  - **Concrete miscount for unsafe integers:** the local sizer serializes input `9007199254740995` as `"9007199254740996"` (double-precision rounding), so the "canonical bytes" it charges against the budget do not even correspond to the supplied integer.
- **Impact:** (1) A `.strict()` security-critical envelope fails **open**, admitting extension values that have **no** RFC-8785-subset canonical form. (2) The "≤16,384 RFC-8785-canonical bytes" invariant is meaningless for such values (phantom / miscounted size), a budget-bypass surface. (3) Downstream break: the same job, once embedded in an event and digested via the authoritative E0/PRT-004 canonicalizer (`eventDigest = SHA-256 of RFC-8785 canonical JSON`, amendment line 95), will **throw** — a job PRT-003 declared valid cannot traverse the event pipeline. This is exactly the silent two-canonicalizer divergence the program's cross-implementation cross-check (line 97) exists to prevent, and the implementer's self-report claim that "the byte semantics already match the amendment" holds only for in-subset values.
- **Affected tickets:** PRT-003 (fix now); PRT-004 (the shared `canonical-json.ts` unification is the eventual convergence, and its cross-implementation digest cross-check would surface any residual gap).
- **Root cause / resolution:** The local sizer is a third canonicalizer whose accept/reject boundary was never aligned with the frozen E0 authority. **Required fix (within PRT-003 scope, no PRT-004 pre-emption):** make an extension value that is not canonicalizable under the frozen RFC-8785 subset **fail closed** — reject non-integer numbers, non-safe integers, and lone/broken surrogate strings, matching E0's `canonicalizeNumber`/`canonicalizeString` reject behavior (making the local `canonicalJson`/`canonicalString` throw on those is minimal, since `addExtensionArrayIssues` already converts a canonicalizer throw into a "not canonicalizable" issue; ideally also flag the offending path in `addExtensionValueStructureIssues`). Add tests asserting float / unsafe-integer / lone-surrogate extension values are rejected.
- **Status: RESOLVED (resolving revision `e62921b1743f9cbc33e6ecf79348a7f4bf5d5483`).** `job.ts` `canonicalString` now throws on a lone high surrogate (not followed by a low) and on a stray low surrogate; `canonicalJson` throws on `!Number.isInteger` (float) and `!Number.isSafeInteger` — byte-for-byte with the E0 authority's `canonicalizeString`/`canonicalizeNumber`, and the existing `addExtensionArrayIssues` try/catch turns the throw into a fail-closed "not canonicalizable" `custom` issue at the extension value path. Independently re-verified at PRT-003 review **attempt 2 (`approved`)**: `1.5`, `9007199254740992`, `"\uD800"`, `"\uDC00"`, `{rate:0.25}`, `[9007199254740992]` now return `success:false` on BOTH `jobEnvelopeV1Schema` and `leaseOfferV1Schema` (nested-job + own-extensions, issue path at the extension value); in-subset values still pass with 23/23 byte-for-byte E0 agreement and the value-budget boundary unchanged (16,384/16,385); valid astral emoji pairs are not falsely rejected. Diff scoped to `job.ts` (+26) + `job.test.ts` (+13 assertions) + ledger; focused 93/93, full 124/124, typecheck/build/boundary all exit 0.
- **Non-blocking follow-up (PRT-004): RESOLVED-IN-FULL.** The local `job.ts` extension byte-sizer was a second canonicalizer duplicating the E0 semantics. PRT-004 Deliverable B unified `job.ts` onto the shared `canonical-json.ts` (single canonicalizer), and Deliverable C additionally extracted the bounded-extension container/refiner into the shared `extensions.ts` (single refiner) — so the package now carries **one** canonicalizer AND **one** extension refiner across job/lease/events. Independently re-verified at PRT-004 review attempt 2 (`approved`, `0a00e3f3a61f1e532b11fb526e209589f7a0fe69`): grep confirms the sole canonicalizer definitions are in `canonical-json.ts` and the sole extension-refiner definitions are in `extensions.ts`; the cross-implementation digest cross-check reproduces all 50 committed `eventDigest`s across 9 fixtures with zero mismatches. This follow-up is complete; no residual drift.

## E1-F005 — PRT-004 worker-event extensions under-enforce the ONE bounded-extension container: `workerEventV1Schema` fails OPEN on value depth/array-items/object-keys/key-bytes and has NO combined budget (job/lease enforce all five)

- **Severity:** High (fail-open at a `.strict()` inbound worker→control-plane wire envelope — the batched, high-volume, less-trusted surface the bounded container exists to fence — on five of the amendment's exact per-value/aggregate extension limits).
- **Blocks gate:** No (epic gate). **Blocks PRT-004 approval:** Yes (reviewer disposition `changes_requested`).
- **Discovered during:** PRT-004 independent review (reviewed revision `590f8162f1234beffd83a759c03bc743357181d1`).
- **Context:** The hardening amendment ([implementation-plan.md](implementation-plan.md) line 71) defines THE bounded-extension container with EXACT limits — "at most 16 extensions; namespace 1–100 UTF-8 bytes; schema version 1–1,000,000; each value has at most **8 container levels, 128 array items, 64 object keys, 100 UTF-8 bytes per key**, and 16,384 RFC-8785-canonical UTF-8 bytes; the **combined canonical value budget is 65,536 bytes**." PRT-004 Step 3 (line 962) requires the worker-event base to carry "**the explicit bounded extension field**" — the same phrase PRT-003 uses for the job/lease envelopes (lines 844/866) and the same ONE container. No E1 decision sanctions a lighter event variant.
- **Evidence (independently reproduced against the reviewed revision, built `dist/`):** `events.ts` applies a bespoke `refineEventExtensions` (lines 383–410) to every event's `extensions` instead of the job/lease `addExtensionArrayIssues` (`job.ts` 219–252). It enforces only count ≤16, unique namespace, unknown-critical-fails-closed, recursive credential-key rejection, and per-value canonical ≤16,384 bytes — and OMITS the value structural walk (`addExtensionValueStructureIssues`) and the combined budget. Comparing the built `workerEventV1Schema` vs `jobEnvelopeV1Schema` on identical extension arrays:

  | Extension value | `workerEventV1Schema` | `jobEnvelopeV1Schema` |
  |---|---|---|
  | container depth 9 | **accepted** | rejected |
  | 129 array items | **accepted** | rejected |
  | 65 object keys | **accepted** | rejected |
  | 101-UTF-8-byte key | **accepted** | rejected |
  | combined >65,536 bytes (5 × 13,200) | **accepted** | rejected |
  | per-value 16,385 canonical bytes | rejected | rejected |
  | namespace 101 bytes / schemaVersion 0 or 1,000,001 / 17th ext / unknown `critical:true` / recursive credential key | rejected | rejected |

  The first five DIVERGE (event fails open where job fails closed); the rest agree. (The shared `wireExtensionSchema` — namespace/schemaVersion/critical shape — is common, so those agree; the divergence is exactly the per-value structural + combined limits carried only by `addExtensionArrayIssues`.)
- **Impact:** (1) A `.strict()` inbound wire envelope admits extension values with no bound on nesting depth, array/object breadth, or key size, and no aggregate budget. (2) The combined-budget gap is *worse* on events than on jobs: events are submitted in **batches of up to 500** and the batch schema imposes no extension budget either, so one event may carry 16 × 16,384 = 262,144 bytes (4× the intended 65,536) and a single batch ~131 MB of extension bytes — an inbound amplification/DoS surface. (3) The depth gap admits ~8,000-level nesting within the 16 KB per-value budget — unbounded-by-contract recursion during the recursive `canonicalizeJsonV1` validation itself and in downstream receiver-side digest recompute (JOB-005). (4) It re-creates the exact anti-pattern E1-F004 closed for the canonicalizer: a SECOND, divergent implementation of the ONE container contract on a wire surface.
- **Affected tickets:** PRT-004 (fix now). Same class carries forward to any later surface that carries `extensions`.
- **Root cause / resolution:** `refineEventExtensions` is a partial re-implementation of the bounded container that silently dropped the value-structure and combined-budget checks. **Required fix:** make the worker-event `extensions` enforce the FULL amendment container (depth ≤8, ≤128 array items, ≤64 object keys, ≤100 UTF-8 key bytes, ≤16,384 canonical bytes per value, combined ≤65,536), identically to job/lease. **Preferred (same lesson as the single canonicalizer):** extract the container refinement into a SINGLE shared module/schema used by `job.ts`, `lease*`, and `events.ts`, so the ONE contract has ONE implementation; delete the bespoke `refineEventExtensions`. Add event-schema tests asserting depth 9 / 129 items / 65 keys / 101-byte key / combined >65,536 each fail at boundary+1 and pass at the boundary — the same boundary battery `job.test.ts` already carries. Consider whether the batch schema also needs an aggregate cap (out of scope for the per-event fix but worth a note).
- **Status: RESOLVED** (resolving revision: the E1-F005 fix commit on `claude/epic-e1-worker-protocol-6a5d96`; repository history pins the SHA). The ONE bounded-extension container — element schema `wireExtensionSchema`, array schema `wireExtensionsArraySchema`, and the FULL refiner `addWireExtensionArrayIssues` (the reviewer-correct job refiner + its value structural walk relocated verbatim, byte-identical) — now lives in the new single-source-of-truth module `packages/worker-protocol/src/extensions.ts`. `job.ts` (envelope + lease) and `events.ts` all import and apply `addWireExtensionArrayIssues`; the bespoke `refineEventExtensions` is deleted. `workerEventV1Schema` now enforces the full container identically to `jobEnvelopeV1Schema`: `events.test.ts` adds the boundary battery asserting depth 9 / 129 array items / 65 object keys / 101-UTF-8-byte key / combined >65,536 each REJECT and the exact limits (depth 8 / 128 / 64 / 100-byte / 16,384 / combined 65,536) ACCEPT, and that the five previously-accepted violating shapes now fail on the event schema. Job behavior is byte-identical (relocation only; all 60 job tests incl. the 13 E1-F004 out-of-subset + 16,384/16,385 boundary still green). The package now carries ONE canonicalizer AND ONE extension refiner. Recursive plaintext-credential rejection stays at the envelope level via each consumer's `addForbiddenWireKeyIssues` (unchanged, byte-identical to the reviewed job topology). A batch-level aggregate cap is intentionally left to PRT-007 (per-operation transport concern), per the coordinator directive. **Independently re-verified and CONFIRMED RESOLVED at PRT-004 review attempt 2 (`approved`, reviewed revision `0a00e3f3a61f1e532b11fb526e209589f7a0fe69`):** the adversarial event-vs-job probe shows the five previously-diverging shapes (depth 9 / 129 array items / 65 object keys / 101-UTF-8-byte key / combined >65,536) now REJECT on BOTH `workerEventV1Schema` and `jobEnvelopeV1Schema` and ACCEPT at the exact limits (8/128/64/100/16,384/65,536) — no remaining divergence; a normalized diff proves the refiner was relocated verbatim (job byte-identical, 60/60 job tests green); grep confirms exactly ONE canonicalizer AND ONE extension refiner; the digest cross-check is unaffected (9 fixtures / 50 events / 0 mismatches); focused 144/144, full 208/208, typecheck/build/boundary all exit 0.
- **Note on Deviation #3 (non-blocking, corrected):** the reviewer is correct — the implementer's original Deliverable-B rationale claimed `addExtensionValueStructureIssues` "independently rejects a non-plain-object extension value," which is factually wrong: a `Date`/`Map`/class-instance extension value is **accepted** by BOTH surfaces (`Date`/`Map` → `"{}"`) because `isPlainObject` and the canonicalizer's `typeof==="object"` branch are equivalent after the null/array checks, so the old local `canonicalJson` `isPlainObject` gate and the shared `canonicalizeJsonV1` agree on ALL inputs and the `{}`-vs-throw divergence never existed.
