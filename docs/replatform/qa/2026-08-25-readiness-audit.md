## 4. The decisions, judged

**(a) Reuse `createWorkerSessionAuthenticator`, hand-write only the platform-physical denial. Correct, and the best decision in the set.** I read the authenticator end to end. It performs the guards, including a scope check at `:165` the hand-written draft omitted, and it genuinely does not deny a platform-physical principal — `claims.organizationId === null` returns a valid principal at `:180-182`. So R1 is a real delta, not ceremony. The alternative — a second authority surface that can drift from the shipped one — is the failure mode §3.3 already refuses on the identity question. **The cost is named honestly and is real:** `WorkerSessionError` collapses nineteen conditions into two operator codes (`:47-52`), so the route loses refusal granularity and the guard-ordering argument had to be deleted rather than kept. That is the right trade, and D-1 states it rather than hiding it.

**(b) Resolve E4-F012 with an `onSessionMinted` sink plus `renew(current)`. Right mechanism, incomplete decision, and the heading over-claims.** The I13 argument is sound and I verified it: the docblock at `enroll-once.ts:140-145` protects the *returned aggregate*, `result` is already live in memory from `:273` to the frozen return at `:311-319`, and `SessionStore` holds the token in a private `#current` (`identity/session.ts:66`) whose only log read is `prev?.targetId` (`:152`). The optional/required asymmetry is genuinely clever: the sink is optional so a test can kill it, the bootstrap dep is required so a compiler kills it. **But cost item 6 establishes that the sink covers only the enrolling boot on `os_keychain` custody — a minority of boots and zero shipped containers — and the majority case is a named dependency with no body, no route and no owner.** A section titled "DECIDED — where slice 2's FIRST session comes from" answers the question for the minority and converts the majority into a compile error. That is progress and it is not an answer. Say so in the heading, and add the missing S2-A1 negative assertion.

**(c) Insert Sprint 2.5 and move the production session wiring into it. Correct, and it dissolved a genuine cycle.** As first written, Sprint 2.5's done-condition ("a production caller") was unreachable because the only production `SessionStore` construction lived in Sprint 3. Moving the identity + store construction earlier is the only resolution that does not make one sprint's acceptance depend on the next. **The cost is that it silently re-scopes a 1,549-line plan that was never edited to match** — slice 2b still builds `SessionStore(..., initial = null)` in §4's diagram, Step 2, Step 6 and Step 7, its §7 row 7b asserts *"no key derived, no SessionStore"*, and §10's entire zero-residue argument depends on 2b owning that construction. A grep of slice 2b for "Step 0" or "re-scope" returns nothing. The go-book carries the instruction; the plan that executes it does not.

**(d) Leave E4-F013 deliberately unowned. Correct, and the only honest option.** E4-F013 is a hole in the ownership guard itself (`scripts/lib/finding-ownership.mjs:118` tests only that `ownerStillOpen` is a non-empty string — I read it), so no product ticket is its natural owner and attaching one would be the false ownership claim the register exists to prevent. `check-finding-ownership.mjs` prints it on every green run, which is the mechanism working as designed. **The cost is that Sprint 1 relies on that hole without saying so:** once `WRK-010-result.md` exists, E4-F007 and E4-F012 hit the already-shipped arm and pass only because their `ownerStillOpen` prose is non-empty. The Sprint 1 prompt says *"Do not touch its status or its key"* and stops. One added sentence closes it.

**(e) Write WRK-011 now rather than plans for Sprints 4 and 5. Correct, and I'd defend it against the obvious objection.** The dependency is not preference: `finding-ownership.json`'s own `E4-F010` entry records that WRK-011's success path replaces `profile_hash`, which `worker-session-auth.ts:167` compares to the session claim (and `job-leasing.ts:259/:297`), so the caller's own session dies the instant the row is written — and there is no `SessionStore` to hold the replacement until WRK-010 slice 2 ships one. That pins it after 2.5. And without it, Sprints 3 and 4 execute against a fleet that provably cannot be offered work: the enrolled all-zero capacity is a hard `Math.min` ceiling at `job-leasing.ts:566`, so zero lease candidates come back before the matcher is reached. Sprint 5 would have been the first place anyone learned whether the fix was feasible. **The cost is the one nobody paid: writing WRK-011 without re-scoping slice 2b created the BLOCKING contradiction above.** A plan inserted before another plan owes that other plan an edit.

## 5. The riskiest thing nobody has written down

**The go-book has become a document whose corrections outnumber its claims, and its correction mechanism is prose — which means the next stale sentence will be found by a reader, not by a check.** Look at what the fix wave actually produced: `E4-F011`'s heading now says THREE, its body says SIX, and its closing line still says *"one environment variable"* — three numbers for one quantity inside a single register entry, all at tip, all committed. DEP-010 says two in seven places, slice 2b says four in §0 and three in §9 and six in §2, and the go-book carries the corrected six in a blockquote with *"two env vars from taking real leases"* in the sentence immediately beneath it. **Every one of those is a document about a gate count, and not one of them is a check.** This programme built five registers precisely because it learned that a claim nobody can falsify goes green over nothing — and then it wrote the single most-repeated, most-contradicted, most-load-bearing fact in the whole plan set (how many things stand between a shipped desktop and live dispatch) into prose in six documents with no checker at all. `check-gate-clause-wiring.mjs` counts callers. `check-finding-ownership.mjs` counts non-empty strings. Nothing counts gates. The honest number is derivable mechanically — the union of `DispatchRefusalReason` in `compose-dispatch.ts` minus the ones a given root already satisfies — and a twenty-line checker that reads the union from source and fails when a document states a different total would have killed all four discrepancies at once, plus the E4-F011 regression Step 11 is currently scheduled to write. **Until that exists, every gate-count sentence in this plan set is exactly the artifact class the programme's own §2.3 calls its most common defect, and the reason nobody has noticed is that the correction blockquotes read like rigour.** Add the checker before Sprint 2, not after.
