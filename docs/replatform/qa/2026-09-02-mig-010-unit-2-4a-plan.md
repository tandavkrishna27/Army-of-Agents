## Why this plan opens with probes

Three design rounds have now produced a mechanism that looked correct, passed review, and was wrong:
a company-scoped pass that could not call an org-bound function; an optional watermark that *opens*
the gate; a total that vanishes exactly when it is needed. **All three passed review. All three were
caught only by running PostgreSQL.**

So Task 1 measures, and every later task cites a probe result rather than an expectation. If a probe
disagrees with this plan, **the probe wins** — stop and report rather than reconciling the code to
the document.

## Task 1: Probes — measure before building

**Files:** Create `server/src/__tests__/mig-010-unit-2-4-probes.integration.test.ts`

These are throwaway-shaped but permanent: they pin PostgreSQL behaviours the design depends on, so a
future reader does not have to re-derive them. Use the `startMigratedDatabase` harness and its
`admin` client; create scratch functions in a temp schema, not `public`.

- [ ] **Step 1: The one-row contract (§11.1)**

Prove both halves in one test: a `RETURNS TABLE (ids uuid[], total bigint)` built from
`array_agg` + `count` returns **exactly one row even when the narrowed set is empty**, while the
`RETURNS TABLE (id uuid, total bigint)` shape returns **zero rows** in that case.

```ts
it("[§11.1] a set-returning shape loses the total on the empty set; the one-row contract keeps it", async () => {
  // …create both shapes over the same fixture, call each with a watermark that predates every row…
  expect(setShapeRows).toHaveLength(0);            // the total is UNOBSERVABLE — the §10.3 defect
  expect(oneRowShape).toHaveLength(1);
  expect(oneRowShape[0]).toMatchObject({ ids: null, total: 3n });  // or String(total), driver-dependent
});
```

★ Record in the test what the driver actually returns for `bigint` (`bigint` vs string) — 2.4b's
comparison depends on it and getting it wrong is a silent `"3" > 0` bug.

- [ ] **Step 2: The overload trap (§11.2) — the fail-open, measured**

With a 2-arg function AND a 3-arg overload whose third parameter is **required**, a 2-arg call must
resolve **silently to the 2-arg function** (no 42725). Assert that, then assert that after
`DROP FUNCTION …(uuid, uuid)` the same call raises **42883**, not 42501.

★ This is the test that justifies the DROP in 2.4b. Without it the reason on record is wrong.

- [ ] **Step 3: Return-type immutability**

`CREATE OR REPLACE` changing only the `RETURNS TABLE` shape must raise **42P13**. This is why 2.4b
cannot avoid a DROP even at unchanged arity.

- [ ] **Step 4: `identity_arguments` rendering**

A `timestamptz` parameter must render as `timestamp with time zone`. Assert the exact string — the
manifest compares with exact equality and a `timestamptz` entry is a fatal every-boot failure.

- [ ] **Step 5: Clock semantics**

Prove `now()` is transaction-start and `clock_timestamp()` is not, inside one transaction. Then prove
the direction that matters: a row inserted by a transaction that **began before** a watermark read
carries `created_at < watermark` even when it **commits after** — i.e. it stays IN scope, which is
the fail-closed direction.

## Task 2: The marker table

**Files:** `packages/db/src/schema/…`, a new migration, the keystone constants.

- [ ] **Step 1: Derive the columns from the sentence, not from convenience**

§11.4: *"latest marker" only means "latest COMPLETED pass" if the marker records completion, scope
and identity.* So, at minimum: the organization, the company, the **snapshot instant** (DB clock),
the **key generation** observed, a **completion** marker, and `created_at`. A pass that aborts must
leave **no completed marker**.

★★★ **The generation column is `NOT NULL`, with an explicit `'ungenerationed'` sentinel** — design
§13, and it is not a style choice. `key_generation` is nullable everywhere else in this system, NULL
is a NORMAL value (a company with no default e2b key), and the shipped gate's
`r.keyGeneration !== null && …` filter therefore treats NULL as *not superseded* — filed as
**E7-F005**. A nullable marker column would concentrate that hole into a single row, where one value
disables the whole check. Make it unrepresentable here.

- [ ] **Step 2: Search for an existing operator-metadata table to extend before minting one.**
  Record what you found and why it does or does not fit. A new table is the expected answer; an
  unexamined new table is not.

- [ ] **Step 3: Generate the table with `pnpm db:generate`, then hand-append ONLY the C14 parts**
  (grants, `ENABLE`/`FORCE ROW LEVEL SECURITY`, policies) with a per-statement comment on each.
  Model: `0256_dizzy_bedlam.sql`. Schema DDL is **never** hand-authored.

- [ ] **Step 4 ★: Reconcile the keystones, all of them.**

A new operator-metadata table must be taught to every constant and boot assertion that enumerates
them, or boot fails with an opaque error. Find the full set by tracing what
`legacy_resource_reconciliation` touches in `server/src/db/job-control-legacy-grants.ts` and
`server/src/db/distributed-execution-databases.ts`. **`POLICY_COUNTS` key order must match
`RLS_RELATIONS` order** — a mismatch is invisible in review.

★ Put the new grant in its **own** `*_OPERATOR_GRANTS` constant. Adding it to
`JOB_CONTROL_LEGACY_GRANTS` retroactively rewrites applied migrations 0213/0214 and reds a
byte-identity test ~30 minutes into `verify`.

## Task 4: The pass writes the marker

**Files:** `server/src/services/legacy-resource-reconciliation.ts` + its store + the CLI.

★ **This task got SMALLER, not bigger, once §12 landed.** An earlier revision required a per-company
transaction and a rotation abort. Both are gone. §12 shows the rotation trap is a standing condition
with an unbounded window — any rotation *after* a clean pass bricks the company just as thoroughly as
one during it — so a transaction, which can only cover the pass's own duration, was a mechanism
fitted to the wrong window. The fix is that the **marker** carries the generation and the gate reads
it there (2.4b). Once that is true, a rotation is ordinary recoverable staleness and the pass needs
no abort at all.

**Do not add a transaction seam in this unit.** It is not the fix, it changes the store contract, and
scope that is not the fix is how a unit stops being reviewable.

- [ ] **Step 1: The snapshot instant**

Read it from the **database** before listing anything, and thread it through the pass. Probe 1.5
established which of `now()` / `clock_timestamp()` you want and which direction each fails in — cite
that result here rather than re-deciding.

- [ ] **Step 2 ★: The marker carries the generation — that is the whole fix**

The pass already reads `currentKeyGeneration` **once per company** and threads one value into every
record for that company (`legacy-resource-reconciliation.ts:410-414` — verify this before relying on
it). Write that same value into the company's marker.

That is all this unit does about rotations. The record's own `key_generation` column stays exactly as
it is: it is history, and rewriting shipped semantics is not required to fix this. It simply stops
being what the gate reads, in 2.4b.

- [ ] **Step 3: The marker is the pass's LAST write for a company**

After every record for that company. Nothing may observe a completed marker for a company whose
records are not all on disk. A crash between records and marker leaves "records, no marker", which
the gate reads as *not reconciled* — the fail-closed direction, and the re-run completes it.

- [ ] **Step 4 ★★★: The test that proves recovery — the one the old remedy would have failed**

This is the unit's most important test, and it is now writable without the gate:

```
run a clean pass                 -> a marker exists for the company, carrying generation G1
rotate the provider key to G2    -> records unchanged (still G1), marker unchanged (still G1)
re-run the pass                  -> a NEW marker exists carrying G2
                                 -> the RECORDS are byte-identical to before (onConflictDoNothing)
```

The last two assertions are the point. The new marker proves recovery is possible; the unchanged
records prove it did **not** depend on re-tagging them — which is exactly what the append-only
crosswalk makes impossible and what §12 identified as the real trap.

★ Assert the record set is unchanged by **comparing every row**, not by counting. A count is equal in
both the working and the broken world.

- [ ] **Step 5: A partial pass is re-runnable and converges**

Interrupt a pass between records; re-run; assert the full record set and exactly one completed marker.
