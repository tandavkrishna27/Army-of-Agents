# DECISION REQUEST — DAT-007 item #1: a fence-bound run-JWT resolver for the distributed `/mcp` auth path

**Date:** 2026-09-19
**Decision:** **DAT-007 item #1 / CLI-008 Unit C precondition** — *"On the distributed (remote-worker E2B) lane, what server-side seam re-proves that the run presenting a per-run agent JWT at `POST /companies/:cid/mcp` is STILL the current holder of a live lease/fence before its tool call is admitted — where does that check run, and must it land before the distributed tool surface goes live?"*
**Ticket:** `DAT-007` (owns the run-scoped MCP auth seam), epic `E5 — Workspaces/Secrets`; it is the named critical-path precondition for `CLI-008 Unit C` (E7 — coding workload on E2B).
**Adjacent, ratified, and NOT relitigated here:** the **DE-08 / E8-F003 sandbox-egress ruling** (`docs/replatform/DECISION-REQUEST-de08-sandbox-egress.md`, RULED 2026-09-11; recorded in `distributed-execution-threat-controls.json` DE-08 `authorization`/`control`, amended 2026-09-11). This paper reads that ruling as settled — provider-level egress denial is unavailable at the managed-shared tier — and prices against it; it does not re-open it. The companion **CLI-008 Unit C tool-reachability decision paper** (`docs/replatform/DECISION-REQUEST-cli-008-unit-c-tool-reachability.md`, itself still *awaiting founder ruling*) named *this* resolver ("DAT-007 item #1") as the gate that turns the distributed tool surface on; this paper makes that resolver ruleable.
**Status changes made by this document:** **NONE.** No finding is closed, struck, re-dispositioned or re-owned; no `deliveryStatus` moves; no clause in `distributed-execution-threat-controls.json` is edited; no `gate-clause-wiring.json` enrolment is added. **Choosing among the options in §3 IS the decision being requested**, so this paper makes none of them. **Production code written: none. Unit F is untouched and this does not move it.**

## 0. The facts stated first, before the options

1. **The distributed tool credential is a run-JWT that carries no lease and no fence.** `createLocalAgentJwt(agentId, companyId, adapterType, runId)` (`server/src/agent-auth-jwt.ts:68`) mints claims of exactly `{ sub, company_id, adapter_type, run_id, iat, exp, iss, aud }` (`:73-82`) — agent, company, and run identity, and nothing about a lease, an attempt, a generation, or a fence token. (The `LocalAgentJwtClaims` type also permits an optional `jti` at `:17`, but the minter never sets it — see §3's revocation-set note.) `verifyLocalAgentJwt` (`:95`) requires those same claims (`:120`) and its **only** liveness gate is TTL expiry — `if (exp < now) return null` (`:123`) — against a default TTL of **48 hours** (`AOA_AGENT_JWT_TTL_SECONDS`, `60 * 60 * 48`, `:34`). Within that 48h window a signed run-JWT is accepted regardless of whether the run it names is still executing.

2. **The `/mcp` auth path closes wrong-tenant and closes stale/replaced zero times.** Every request to `POST /companies/:companyId/mcp` (`server/src/mcp/server.ts:428`) re-runs `ensureProtocolAccess` (`:446`), which asserts `actor.companyId !== companyId → forbidden` (`:261-263`) and then calls `assertCompanyAccess`, whose agent branch is again only `req.actor.companyId !== companyId → forbidden` (`server/src/routes/authz.ts:44-49`). The middleware that minted the actor already dropped a JWT whose agent row fails `agentRecord.companyId !== claims.company_id` (`server/src/middleware/auth.ts:347`, binding the claimed company to the agent's real company) or whose agent is `terminated`/`pending_approval` (`:352`). And on the broker dispatch path the context resolver re-asserts `agentRow.companyId !== companyId → forbidden` (`server/src/mcp/broker-tool-context.ts:177-179`). **Every one of these is a company-identity equality check.** None of them — nor anything else on the path — consults the run's lease, attempt, or fence. The `runId` is threaded through for audit and context (`middleware/auth.ts:362`, `server.ts:474-479`) but is never liveness-checked.

3. **The one resolver that DOES prove lease/fence currency cannot be reused, but the link it would need exists.** `resolveWorkerFenceContext` (`server/src/services/worker-fence-context.ts:86-92`) demands a `VerifiedWorkerOperation` — device proof carrying `workerId`/`targetId`/`deviceThumbprint`/`proofId` (`server/src/middleware/worker-operation-proof.ts:5-16`) — **plus** a presented `{ leaseId, jobId, attempt, fenceToken }` tuple (`:89`); it verifies a *worker control-plane* op that carries all of that in the request body. The `/mcp` run-JWT presents **none** of it (fact 1). So it is not directly reusable — the same conclusion DAT-007 reached at source ("NOT FEASIBLE as 'reuse' — needs a NET-NEW resolver + a design decision", `DAT-007-result.md` §2, correcting the design's earlier "reuse `resolveWorkerFenceContext`" framing at `DAT-007-design.md` §3/§4). But the missing link is present in the data: a distributed run is a `task_run` job whose `sourceIntent.runId` equals the JWT's `run_id` (`server/src/services/job-leasing.ts:134,141` at HEAD — the register's `:111` is a stale line number), so a **net-new `runId → job → active-lease/fence` resolver** keyed on the run-JWT alone is feasible.

**What this settles for the decision.** The transport already exists (the brokered `aoa` HTTP entry → `${apiBaseUrl}/companies/${companyId}/mcp`, `Bearer` run-JWT, no `DATABASE_URL`, `server/src/services/internal-agent/cli-mode.ts:339-342,335-336`), the frozen worker wire needs **no new op** to carry a tool call (`WORKER_PROTOCOL_OPERATIONS` is 10 ops with no tool op, `packages/worker-protocol/src/transport.ts:757-768`), and the network **cannot** fence the credential (DE-08, §2). So the open question is not "can a distributed sandbox reach the tools" — it is **"where does the server re-prove the run is still fence-current, how is that check mounted, and must it exist before the surface goes live."** That is a founder decision.

## 1. The gap, measured by symbol

The denial taxonomy the endpoint must enforce has three members. **One is closed; two are open.**

- **wrong-tenant — CLOSED (at the app layer, today).** A run-JWT for company A presented at company B's `/mcp` URL is refused at `server.ts:261-263` and again at `authz.ts:44-49`; a forged claim is dropped at `middleware/auth.ts:347` (the agent row's company must equal the JWT's claimed company); and the broker path re-refuses at `broker-tool-context.ts:177-179` — each a uniform `forbidden` (cross-tenant ≡ missing, no existence oracle). A database-enforced org-RLS backstop *exists in the codebase* (`runInTenant` on the non-owner `aoa_app` role, NOSUPERUSER/NOBYPASSRLS, `server/src/db/tenant-context.ts:9,46`) but is **dormant behind the default-off `AOA_DISTRIBUTED_EXECUTION_ENABLED` flag AND not yet wired onto the `/mcp` path** — "the MCP broker path is company-scoped today (app-level `agent.companyId===companyId`), NOT org-RLS … DAT-007 adds the org-tenant backstop" (`DAT-007-design.md` §6). So RLS is a *future* second wall, not an active one; the app-level identity close is sufficient and stable on its own. This case needs no currency resolver.

- **stale (lease lost) — OPEN.** A run whose lease has expired or been revoked still holds a validly-signed, unexpired run-JWT and a live `agents` row under the right company. Every check in fact 2 passes. If it calls a broker-registry tool it reaches `resolveBrokerToolContext` (`broker-tool-context.ts:171`), gets a full `ToolContext` (`:204-217` org / `:231-244` crew), and executes on the control plane against the company's real data — for up to the JWT's remaining TTL (`agent-auth-jwt.ts:34`). **The exposure is not confined to the broker registry.** An agent-source run-JWT with a `runId` also reaches the *outbound* tool path (`server.ts:780+`), where `memory.search`/`memory.get`/`memory.retain`/`memory.write` are `agent`-allowed (`server/src/mcp/tools/index.ts:54-60`), `ask_human`/`ask_founder` are `agent`-only (`:67-68`), and any tool not listed in `toolAllowedActors` is "open to all authenticated actors" (`server.ts:786-787`) — all dispatched **without ever entering `resolveBrokerToolContext`**. Both dispatch paths are equally uncovered by any currency check.

- **replaced (attempt superseded) — OPEN.** When a job's attempt is superseded by a newer attempt (retry/reassignment), the superseded sandbox is in the same position on both paths: its run-JWT is still signed and unexpired, its agent row still matches the company, so its tool calls are still admitted. Nothing on the `/mcp` path compares the presenting run against the job's *current* attempt/lease holder.

**Consequence.** At the managed-shared tier a stale or replaced distributed sandbox can keep reading memory, creating tasks, asking humans, and writing artifacts through *either* dispatch path against a live company until its run-JWT simply times out — with no network layer to stop it (§2). The wrong-tenant wall is real; the **currency** wall does not exist. Closing it is exactly the net-new resolver DAT-007 deferred (`DAT-007-result.md` §4: "a net-new `runId → job → active-lease/fence` resolver keyed on the run-JWT … the coarse non-disclosing denial for stale/replaced/wrong-tenant, and a decision on whether the MCP seam adopts it or a distinct auth path").

## 2. The constraints — DE-07 requires the scoping; DE-08 removes the fallback

Two ratified threat-register clauses fix the shape of any acceptable answer.

### DE-07 — the tool credential MUST be lease- and fence-scoped (it is a stated requirement, not a nicety)

DE-07 (`Control plane <-> secret and MCP OAuth broker`, `distributed-execution-threat-controls.json` DE-07, `:155-176`) sets `authorization: "handles are lease- and fence-scoped; the broker owns refresh"` (`:161`), and its `deliveryStatus` is **`partial`** (`:176`). The run-JWT the distributed sandbox presents to the broker **is** exactly such a handle — "a worker or sandbox holding an opaque execution handle" (`:159`). DE-07 therefore does not merely suggest fence-scoping; it **requires** it of the credential before it is honored. On the distributed lane that scoping is precisely item #1. Shipping the tool surface without it leaves DE-07's `authorization` clause unmet for the distributed caller.

### DE-08 — there is no network backstop for a stale credential at this tier

DE-08 (`Sandbox <-> network egress`, `:180-201`) was **amended 2026-09-11**: default-deny egress is "UNAVAILABLE at the managed-shared tier (measured, both network constructions inert)" (`authorization`, `:186`), the block-range integrity clause is "vacuous at this tier — there is no block to rebind past" (`:188`), the operative control is "the credential taxonomy (no exfiltratable secret in the VM), NOT egress denial" (`:193`), and `deliveryStatus` is **`not-delivered`** (`:200`). The consequence for us is decisive: a run credential that has gone stale inside the guest **cannot be fenced at the network layer**, because at this tier nothing denies egress. The bound on a credentialed distributed sandbox must be the **credential's own currency, enforced server-side** — which is this resolver.

### Why the wrong-tenant close does not also close stale/replaced

The wrong-tenant close is an **identity equality** (`agent.companyId === companyId`, the sites in §1; plus, on the distributed lane, a dormant org-RLS backstop DAT-007 would wire — not active on this path today). Identity equality is time-invariant: a run's company does not change mid-flight, so the check that a run belongs to its company stays true whether the run is live, stale, or replaced. **Currency is a different predicate** — "is this run still the holder of a live lease *right now*" — and no equality on a JWT claim can answer it, because the JWT is a static bearer artifact minted once at run start (`agent-auth-jwt.ts:73-82`) and never re-issued as the lease state moves. Only a server-side re-derivation against live lease rows can answer it. That is the whole reason item #1 is net-new rather than a tightening of an existing check. **This gap is distributed-specific.** A local in-process run (`local_trusted`/desktop) resolves `acquireExecutionContext → {sandbox:null, lease:null}` (the U4/S1 contract) — it holds no separable lease that can be lost or superseded while it keeps executing, so its run-JWT currency and its execution currency coincide. Only a remote worker sandbox can outlive its lease (lost) or be superseded by a newer attempt (replaced) while still holding a valid run-JWT, so the currency resolver is required on the distributed lane and is a no-op on the local one. This is why item #1 is a *precondition to arming the distributed surface*, not a live production hole (the surface is off by default behind `AOA_DISTRIBUTED_EXECUTION_ENABLED` and tool-less until Unit C ships).

## 3. The mechanisms, priced

Every option below shares one fixed shape, dictated by fact 3 and DAT-007's own residual: a **net-new `runId → job → active-lease/fence` resolver** that takes the verified run-JWT identity (`agentId`/`companyId`/`runId`) and the control-plane `db`, resolves the `task_run` job by `sourceIntent.runId` (`job-leasing.ts:141`), finds that job's **current** active attempt + live lease, and admits the actor only when the presenting run is that current holder — denying stale/replaced with the **same coarse `forbidden`** the endpoint already returns for cross-tenant (`server.ts:261-263`, `broker-tool-context.ts:177-179`), never a "no such job/lease" oracle (`DAT-007-design.md` §5). It rides the existing MCP transport; it adds **no** worker wire op (`transport.ts:757-768`). What is genuinely undecided is **(Q1a) where in the request lifecycle it runs**, **(Q1b) whether it is mounted into the `/mcp` seam or a distinct path**, and **(Q2) when it must land relative to the tool surface going live**.

### Two mechanisms considered and NOT chosen (recorded so they are not resurrected)

- **Shorten the run-JWT TTL** (`AOA_AGENT_JWT_TTL_SECONDS`, `agent-auth-jwt.ts:34`, env-tunable). This bounds the stale window to the TTL but **does not close the gap**: a lease lost or an attempt superseded one minute after mint still admits the sandbox for the rest of the TTL, a long coding run forces a TTL long enough to reopen the window, and it does nothing at all for the *replaced* case within the TTL. It is a partial mitigation, not a currency check, and is no substitute for the resolver.
- **A push-based revocation set** keyed on run id / `jti` (the run-JWT carries an optional, currently-unset `jti`, `agent-auth-jwt.ts:17,143`), consulted per call, publishing on every lease-loss / attempt-supersede event. This is the same currency guarantee by a different mechanism, but it **fails OPEN** on any missed or delayed revocation-publish event (a stale sandbox stays admitted until the event lands), whereas the pull resolver **fails CLOSED** (absent a confirmed live lease, deny). For a Critical-severity credential the network cannot fence (§2), fail-closed is decisive — a push set is at best a latency optimization layered on top of the pull check, never a replacement for it.

### Q1a — WHERE the check runs: at session establishment (A) vs per tool call (B)

**A load-bearing property first:** the `/mcp` endpoint is **stateless-per-POST**. A single handler (`server.ts:428`) serves `initialize` (`:503`), `tools/list`, `tools/call` (`:674`) and `resources/*`, and it re-runs `ensureProtocolAccess` on **every** request (`:446`). There is no server-side MCP session store keyed to a session id on this path — `initialize` mints no session token (`:503-517`), and `touchClient` records a connection row for telemetry only. This reframes the choice.

- **Option A — resolve once, at session establishment (`initialize`).** Run the resolver in the `initialize` branch (`server.ts:503`); cache a "fence-current" marker for the session.
  - *Latency:* cheapest — one lease lookup per session, none per tool call.
  - *Complexity:* **higher, not lower** — because the endpoint is stateless-per-POST, "the session" is not a thing the server currently keeps, so Option A must **introduce session state** (a server-side store keyed to an MCP session id, invalidation, TTL) that does not exist today. It adds surface, not removes it.
  - *Security:* **weakest.** A lease lost or superseded *after* `initialize` is not caught until the next session. That mid-session window is exactly the stale/replaced hole item #1 exists to close. Against a 48h JWT (`agent-auth-jwt.ts:34`) and a long-running coding session, the window is the whole run.

- **Option B — resolve on every tool call, at the request-authorization seam.** Run the resolver once per JSON-RPC POST for a distributed run-JWT actor, at the point that dominates every data-touching method — immediately after `ensureProtocolAccess` (`server.ts:446`), before the method/registry branch split, scoped to `actor.source === "agent" && actor.runId` on the distributed lane.
  - *Why the seam and not the broker branch:* a run-JWT agent reaches company data through **two** server-side dispatch paths — the broker-registry branch (`server.ts:745-768`, via `resolveBrokerToolContext`) **and** the outbound `toolHandlers` fall-through (`server.ts:780+`, gated only by `toolAllowedActors`), where `memory.search`/`get`/`retain`/`write` and every open-to-all tool are agent-reachable *without* touching `resolveBrokerToolContext` (`tools/index.ts:54-60`, `server.ts:786-787`). A check placed only in the broker branch would miss the outbound path entirely; the request-authorization seam covers both, plus `tools/list` and `resources/*`.
  - *Latency:* one additional indexed `runId → job → lease` lookup per POST, folded into auth work the endpoint **already** does per request (the broker-context build already loads a DB row per broker call, `broker-tool-context.ts:176`). Modest and bounded.
  - *Complexity:* **lowest** — no new session state; one mount site that composes with the existing per-request re-auth (`server.ts:446`).
  - *Security:* **tightest** — a lease lost between two calls is caught on the next call, on *every* path; the stale/replaced window shrinks to a single in-flight call.

### Q1b — HOW it is mounted: adopt into the `/mcp` seam (new verifier) vs a distinct distributed-only path

- **Option adopt (into the existing seam).** Add the resolver as a **new server-side verifier** at the `/mcp` request-authorization seam, active only for the distributed lane (run-JWT agent actor with a `runId` on `cloud_auth`/distributed, gated by `AOA_DISTRIBUTED_EXECUTION_ENABLED`), leaving self-hosted and Commander paths byte-identical. It reuses the one `brokerRegistry`, the one dispatch, and the coarse denial shape already in place. This is DAT-007's own framing: "the `/companies/:cid/mcp` auth path cross-checks the run-JWT identity against the live fence context … A stale/replaced/wrong-tenant sandbox is denied with the SAME coarse shape the endpoint already uses" (`DAT-007-design.md` §3 item #1 — with the design's "reuse `resolveWorkerFenceContext`" clause superseded to net-new per `DAT-007-result.md` §2, fact 3).
  - *Complexity:* one new resolver + one call site; no fork of the tool surface.
  - *Security:* the currency check sits on the exact seam every distributed tool call already traverses — nothing can reach either dispatch path around it.

- **Option distinct (a separate distributed-only endpoint).** Stand up a second `/mcp`-shaped path exclusively for worker-dispatched runs, with its own auth.
  - *Complexity:* **high** — duplicates the broker registry/dispatch/denial surface (`server.ts:674-818`) and creates two code paths to keep in parity (the exact drift risk `broker-stdio-parity.test.ts` was built to prevent).
  - *Security:* two surfaces to keep fence-correct; the fork is the liability, not an asset. No benefit over `adopt`, since the transport and registry are identical (§0).

### Q2 — WHEN it lands: block the distributed tool surface until this lands vs turn it on without it

The companion CLI-008 Unit C decision paper recommended landing Unit C's sandbox-side plumbing **inert-until-authorized**, with *this resolver* as the flag that turns the distributed tool surface on (`DECISION-REQUEST-cli-008-unit-c-tool-reachability.md` §5, Q2). This paper is the other half of that contract; the sequencing question is whether the resolver is a **hard gate** on the surface going live.

- **Option block-until (hard gate).** Unit C's credential-carrying plumbing may land inert (its own paper's recommendation), but a distributed sandbox's tool surface is **not reachable** until this resolver is designed, landed, and wired as the admit gate. `E7-F003`'s tools row and `capabilityProven` stay honestly open in the interim.
- **Option turn-on-without.** Flip the distributed tool surface live before the resolver exists — accepting a company-scoped tool surface reachable by a stale/replaced sandbox for the run-JWT's lifetime, with no network backstop (§2). This directly contradicts DE-07 `authorization` (`:161`) and the DE-08 egress concession (`:193`).

## 4. What the pricing forces

Three of the four sub-choices resolve cleanly against the constraints and the stateless-per-POST reality:

- The **stateless-per-POST** endpoint (`server.ts:428,446`) makes **per-call (B)** both the simpler and the safer option, mounted once at the request-authorization seam (`server.ts:446`) so it dominates **both** tool-dispatch paths, and makes session-establishment (A) a net *addition* of session state for a strictly weaker guarantee. B wins on complexity *and* security; A wins only on a latency margin that a single indexed lease lookup makes small.
- The identical transport, registry, and denial shape across lanes (§0, §3) make **adopt** strictly dominant over a **distinct** path — the fork buys nothing and costs a parity surface.
- DE-07's `authorization` requirement (`:161`) and DE-08's removed network backstop (`:193`, `:200`) make **block-until** the only sequencing consistent with the ratified register — a credential the network cannot fence is only as safe as the server seam it is minted against, and today that seam does not exist.

## 5. Recommendation

**Recommended: a net-new `runId → job → active-lease/fence` resolver, adopted into the `/mcp` seam as a server-side verifier, run PER tool call at the request-authorization seam (Option B, `server.ts:446`) for a distributed run-JWT actor — so it dominates BOTH the broker branch (`:745-768`) and the outbound `toolHandlers` path (`:780+`) — denying stale/replaced with the endpoint's existing coarse `forbidden`; and it is a HARD GATE — the distributed tool surface does not go live until this resolver lands, even though Unit C's plumbing may land inert first.** Framed as the founder's choice; the reasoning:

- **Why per-call (B), not session-establishment (A).** The endpoint keeps no session (`server.ts:428,446`), so A must invent session state for a guarantee that still leaves a mid-session stale window — the precise hole (§1). B folds one lease lookup into per-request work the endpoint already does and closes the window to a single in-flight call. Crucially, mounting it at the request-authorization seam covers the outbound `toolHandlers` path (`server.ts:780+`, `tools/index.ts:54-60`) as well as the broker branch, so no agent-reachable company-scoped tool escapes the check. It is the cheaper *and* the tighter option; that is rare, and it is decisive here.
- **Why adopt, not a distinct path.** The transport (`cli-mode.ts:339-342`), the registry, and the dispatch are identical across lanes; a second endpoint only forks the surface `broker-stdio-parity` exists to keep in parity. The resolver belongs on the one seam every distributed tool call already takes.
- **Why a hard gate.** §2 is decisive: DE-07 *requires* the handle be lease- and fence-scoped (`:161`) and DE-08 *removed* the network fallback at this tier (`:193`,`:200`). Turning the distributed tool surface on before the run-JWT is bound to a live fence means a stale or replaced sandbox calls company-scoped tools until its 48h JWT expires (`agent-auth-jwt.ts:34`), with nothing at the network layer to stop it. The wrong-tenant case is already closed at the app layer (`agent.companyId===companyId`, §1); stale/replaced is exactly the currency gap this resolver closes, and it must be closed before the surface is reachable.

**★ The strongest argument against the recommendation.** *A per-call resolver puts a `runId → job → lease` lookup on the hot path of every single tool call, and the distributed coding lane is exactly the workload that makes the most tool calls — a long agent turn can issue dozens of memory/task/artifact calls, each now paying one lease lookup and each now able to fail closed mid-turn on a lease that flickered.* If the founder judges that hot-path cost or the mid-turn fail-closed behavior unacceptable, the coherent alternative is **session-establishment (A) with a short session TTL** — resolve once at `initialize`, cache a fence-current marker for a small bounded window, and re-resolve when it expires — accepting a bounded stale window (the session TTL, not the 48h JWT) in exchange for amortized lookups and turn stability. That is a real latency/liveness trade; it is offered as the named alternative rather than hidden. It does **not**, however, change the sequencing answer: whichever transport is chosen, the resolver must exist before the distributed surface goes live, because the alternative to *some* server-side currency check is *no* currency check, and DE-08 leaves nothing behind it.

## ▣ DECISION REQUEST — DAT-007 item #1 fence-bound run-JWT resolver — **AWAITING FOUNDER RULING**

Two questions; the second is the load-bearing one.

**Q1 — Mechanism: where the currency check runs, and how it is mounted.** Confirm the resolver's transport shape, given the `/mcp` endpoint is stateless-per-POST (`server.ts:428,446`), the transport/registry are identical across lanes, and a distributed run-JWT actor reaches company data through two dispatch paths (broker `:745-768` AND outbound `:780+`).

- ☐ **RECOMMENDED — per-call (B) at the request-authorization seam, adopted into the `/mcp` seam.** A net-new `runId → job → active-lease/fence` resolver runs once per JSON-RPC POST for a distributed run-JWT actor immediately after `ensureProtocolAccess` (`server.ts:446`), dominating BOTH the broker-registry dispatch (`:745-768`) and the outbound `toolHandlers` path (`:780+`) so it covers every agent-reachable company-scoped tool — not just the broker registry — denying stale/replaced with the existing coarse `forbidden`; no new worker wire op (`transport.ts:757-768`); self-hosted/Commander byte-identical; gated by `AOA_DISTRIBUTED_EXECUTION_ENABLED`. Cheapest *and* tightest given the stateless endpoint.
- ☐ **Alternative — session-establishment (A) with a short TTL, adopted into the `/mcp` seam.** Resolve once at `initialize` (`server.ts:503`), cache a fence-current marker for a small bounded window, re-resolve on expiry. Amortizes lookups and avoids mid-turn fail-closed; accepts a bounded stale window and introduces net-new session state. (Must still gate both dispatch paths.)
- ☐ **Reject the seam-adopt topology — build a distinct distributed-only auth path.** *NOT recommended* — duplicates the broker registry/dispatch/denial surface (`server.ts:674-818`) and creates a parity liability with no security benefit over adopting the existing seam.

**Q2 — Sequencing: must the resolver land before the distributed tool surface goes live?
